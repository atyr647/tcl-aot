# Design decisions

Each entry says what was decided, why, and what was measured.  Timings are from a four-core virtual machine whose wall-clock time varies by 20-50 % from
run to run, so where a number decides something it is an instruction count (`valgrind --tool=callgrind`), which does not.  "tcllib workloads" are
small programs built on tcllib 1.21 packages (sha1, md5, crc32, base64, json, csv, textutil, struct, math::statistics, math::numtheory, uuid); they are not
part of this repository.

## 1. Attach to the program's own procs; never alter Tcl

A compiled body replaces nothing the program can see.  The program defines a proc; the runtime recognises the definition and swaps the in-memory bytecode
of that proc for a stub that calls the compiled code in the proc's own frame (see `design.md`).  The alternative, registering compiled code as new
commands, would change `info procs`, `info body`, argument handling, `rename` and error messages, and every caller that expects a proc.  Tcl's source
tree and library are used unmodified; the module only reads Tcl's internal headers and calls its internal functions, all in memory.  `tests/pristine.sh`
checks that the tree compiled against is byte-identical to the 8.6.14 release and that libtcl was built out of it.

## 2. Input is bytecode, not source

The translator works from `tcl::unsupported::disassemble`.  Source-to-C would have to reimplement the compiler's decisions (constant folding, which
commands are expanded inline, exception ranges, the shape of `foreach`/`switch`/`try`) and would diverge from the interpreter in the cases that matter.
The price is that the output is valid for one Tcl release and that the compiler's output depends on state; both are handled by checks (fingerprints,
the build guard) rather than assumed.

## 3. Compiled code is used only while its bytecode is the interpreter's

The compiler emits different bytecode after a package redefines a core command (`::fileutil::find` compiled to 466 instructions at its definition and 474
once the package set was loaded), or while `string` is hidden.  A fingerprint of the interpreter's bytecode at attach time must equal the translator's;
otherwise the proc stays interpreted.  Attaching at the first call (the default) rather than at definition removes most of these mismatches, because the
interpreter itself compiles a body at its first call, and it is cheaper: loading 20 tcllib packages cost 252 M more instructions with eager attach
(157 M of it compiling bodies that were never called).  The fingerprint includes the exact bits of double literals whose printed form does not parse back to
them (`9223372036854775807 / 0.5` is folded to 2^64, which Tcl prints as `1.844674407370955e+19`, one ulp below), because the literal table shares
objects by text.  A rule that followed: no value whose text matters passes through `expr` in the translator.

## 4. Recursion limit at the exact edge

Typed chains (direct calls) carry a depth register initialised from `maxNestingDepth - numLevels` and fail at exactly the interpreter's level, at every
nesting tested (top level, `eval`, `uplevel`, wrapper procs).  A proc entered from the interpreter at the very last level fails one level early: the
stub's own evaluation is checked by the interpreter before any of our code runs.  The error has the same message and code and the same length of error
info; its topmost entry names the callee's first command instead of the calling command.  Closing this would need a patch to Tcl or a raised
`maxNestingDepth`; neither was acceptable.

**Decided by the user (2026-10-31): the edge stays as a named limit.**  A research pass found the only way to close it without a patch to Tcl's sources: replace the
proc command's `Command.nreProc` in memory with a wrapper that adjusts `numLevels` (verified in a prototype).  That writes to Tcl's own `Command` struct, which
conflicts with "never alter Tcl" (decision 1), so it is not done.  It is a stated limit of the system, not an open item: a proc entered from the interpreter at the
very last nesting level fails one level early, with the same message and code.

## 5. Coroutines, `yield`, `tailcall`

Compiled code runs on the C stack and a coroutine suspends by unwinding the interpreter's own stack, which cannot cross a C frame (Tcl answers a `yield`
below a C frame with "cannot yield: C stack busy").  A call that arrives while a coroutine is running is therefore evaluated by the interpreter (the
original body, in the already-built frame, with the stub's nesting level given back), so a `yield` anywhere below a compiled proc works, unless the proc
cannot yield at all.  The translator marks a proc *yield-safe* when everything it runs is known not to reach a `yield`: no `eval`, `uplevel`, `expr` on a
string, no command whose identity is unknown, only built-ins that run no script, and calls only to translated procs that are yield-safe.  Such a proc runs
compiled inside a coroutine, provided every proc it calls (directly or not) is still the compiled one: each entry lists their validity flags, which Tcl's
rename and delete traces clear, so a callee replaced by a proc that yields sends the caller back to the interpreter (`ty_mid` in the differential test, which
fails without the check).

`tailcall` is compiled (the boxed code stores the tailcall list in the frame and returns `TCL_RETURN`, as the bytecode does; the interpreter's frame pop
then schedules it).

Procs that yield themselves are compiled too (decision 20).

## 6. Command frames and error info are the interpreter's

The stub's bytecode keeps the original body's location tables and its pc is moved to the command being run before each command is invoked, so
`info frame`, `-errorinfo` and `-errorline` are equal, including inside coroutines and through `uplevel` and `eval`.  Errors are logged with Tcl's own
`TclLogCommandInfo` from the original bytecode.

## 7. A module is valid only for the Tcl it was compiled against

Generated code compiled without the macros libtcl was built with (`TCL_THREADS`, `USE_THREAD_ALLOC`, `TCL_WIDE_INT_IS_LONG`) took objects from a free list
nothing refills: 80 bytes leaked per loop iteration in boxed code (54 KB per call of `sha1::SHA1Transform`).  `tools/env.sh` takes the macros from the Tcl
build's `tclConfig.sh`; `tbc_check_build`, the first thing every module's Init does, refuses a Tcl whose thread/allocator settings, version or patch level
differ; `tests/guard.sh` builds a module without the macros and requires the refusal; the memory-growth loops of the differential test (`t_leak_g`) fail
by 120 MB when the guard is removed.  Patch-level equality is stricter than the layouts need; only 8.6.14 has been tested.

## 8. Seeing what runs interpreted: `tbc::report`, `tbc::profile`, `tbc::capture`

Whether a program would gain from more compilation depends on what actually runs interpreted, which cannot be known from the source alone.  The three
commands answer it using only Tcl's public interfaces: the report states the fate of every definition (compiled, waiting, `no-code`, `changed`, `differs`,
`refused` with the translator's reason, `demoted`, `early`); the profile counts calls of interpreted procs and scripts evaluated at run time; the capture
writes the procs a program builds at run time as source that can be translated into a second module (`tests/capture.sh`).  Over the tcllib workloads,
320276 calls were of compiled procs and 13 of interpreted ones, and the scripts evaluated at run time were the drivers' own top-level loops; precompiling
literal `eval`/`uplevel` bodies would need the interpreter to accept a bytecode object built for a script, a dependence on Tcl's structures not worth
having for that evidence.  Not done.

## 9. Bodies shorter than the stub stay interpreted

A body of less than 5 bytes of bytecode (the stub is `push1 0; invokeStk1 1; done`) is run faster by the interpreter than by a call into compiled code;
tcllib has several two-to-four-instruction procs.  Growing the bytecode object to fit the stub would risk the interpreter's own structures.

## 10. Where compiled code is not faster, and what was tried

Measured on the tcllib workloads (instructions, compiled against interpreted; 1.0 is parity): sha1 0.93, md5 1.22, crc32 1.03, base64 1.13, json 1.02,
csv 1.04, textsplit 1.00, adjust 0.92, structlist 0.70, structset 0.93, stats 0.91, numtheory 0.75, uuid 1.17 (all 13 results equal the interpreter's).
Self cost of the generated code is 0-20 % of each workload's instructions; the rest is Tcl's own library (the regexp engine, list parsing, `regsub`, hash
tables, the thread allocator), which compiled code calls exactly as the interpreter does.  Consequences:

* **Typed strings and direct untyped calls were not built.**  They act on the generated-code share of string workloads (0-7 %) and on the call machinery
  (at most 5 %).
* **An inline integer fast path at every operator** was tried: 2.5 % fewer instructions, 34 % more code (367 KB to 491 KB for the md5 function), and slower in
  wall time.  Not kept.
* **Unboxed integer temporaries in boxed code** could remove at most the per-operator helper cost (19-25 % of sha1, crc32, stats; under 10 % elsewhere).
  Those procs are in boxed code because typed code ended at `upvar`, arrays and `unset` (see 13); the better fix was to let typed code take those.
* **Bignum arithmetic** (`<<`, `>>`, `&`, `|`, `^`, `+`, `-`, `*` beyond 64 bits) is done natively as the executor does it, not through a micro-bytecode run:
  md5 went from 1.34 to 1.21.
* Typed code is where the gain is: 3.7x to 113x on integer and floating-point loops.  Untyped code with many calls is 0.57-0.75x.

## 11. WebAssembly

The suite was run as a wasm32-wasip3 guest under wasmtime with its default 512 KiB call stack.  It found a defect that cannot show natively: recursion
reaching Tcl's limit of 1000 levels trapped the guest instead of raising "too many nested evaluations", because a failed typed chain is redone in boxed
code where every level is an entry through Tcl's invoke machinery (about 0.7 KB of C stack each).  `TBC_NEST_CAP` (200 when compiling for wasm) makes the
interpreter run calls past that many live compiled entries, with identical results and error info; `tests/nestcap.sh` runs the suite with caps of 1, 3
and 40 natively.  A host that lets guests recurse deeper than 1000 levels still needs a larger call stack.  The four differential calls that stop an
infinite loop with an asynchronous handler marked from a second thread are left out in a guest (`TBC_NOASYNC=1`); a guest has no second thread.

## 12. Size of the output, build time, start-up

* Boxed functions had an entry for every instruction so typed code could hand over anywhere; only the entries some call names are emitted (about 5 % of them), and
  the error-logging sequences are one macro.  The C of a 694-proc module went from 25.6 MB to 19.6 MB.
* `-split N` writes typed and boxed code into separate files and `tools/build-module.sh` compiles them in parallel, boxed code at `-Og` (it gains little
  from more): 158 s to 28 s on four cores, object file 24.8 MB to 16.2 MB, at a cost of 0-3 % more instructions.  All runtime variables are shared across the
  files (`TBC_SHARED`).
* Noticing procs with an execution trace on `proc` passes every body to the trace handler as a list element: startup of 20 packages cost 101.7 M more
  instructions (+12 %).  The module now wraps the C function behind `proc` instead (the same command, so renames and traces of the program follow it):
  +26.6 M (+3.2 %), `trace info execution proc` shows nothing of ours, and a `proc` run through `uplevel` is looked up in the variable frame, as Tcl does
  (the trace handler used the call frame and never attached such procs in eager mode).

## 13. Variables in the frame

Typed code ended at `upvar`, `global`, `variable` and any array element, so a proc using them ran the rest of each call in boxed code: an array sieve was
1.2x the interpreter, an array histogram, array Fibonacci and a counter through `upvar` within 10 % of it.  Such variables now have kind `F` and typed
code works on them in the frame through fast paths that complete or leave everything unchanged and continue in boxed code at that instruction (see
`design.md`).  Instruction counts, compiled against interpreted: sieve 2.1x, histogram 5.2x, array Fibonacci 1.9x, matrix product 1.7x, `upvar` counter
6.6x, `global` counter 10.3x, namespace-variable counter 8.7x, namespace array fill 2.1x; what is left in the array cases is Tcl's hash table (about 40 % of
the sieve).  Consequences worked out with it:

* In a proc with frame variables, typed code can no longer start the whole call over in boxed code when a step fails (earlier steps had effects); the exit
  resumes at the failing instruction.  `tf_resume` increments an array element, then fails in `lindex` on an unbalanced list; the element must be
  incremented once.
* Variables assigned on some paths only were all held boxed in procs that can be asked about their variables by name; they now stay unboxed with an
  "assigned" flag, so loop counters initialised inside an `if` stay in registers.
* `strcat` in boxed code is the executor's own algorithm (one allocation, byte arrays stay byte arrays): building the key `$i,$k` was 36 % slower than the
  interpreter and is now level with it.
* `incr` on a number kept as text (`variable cnt 0`) is taken by the fast path, reading it as the interpreter does.
* Tests: `tf_*` procs (about 600 calls: all key forms, `5`/`05`/`5.0`, missing elements, not-an-array, `incr` on every kind of value, shared values, links to
  scalars, arrays, elements and namespace variables, traces of every kind on the variable, the array and an element, an active array search), a memory-growth
  test that fails with a deliberately leaked key object (11.7 MB), and fifty random programs per fuzz seed mixing typed arithmetic with arrays and the
  three kinds of link.

## 14. Calls from typed code

Calls between translated procs were slower than the interpreter (0.89x, 3000 instructions per call) in any single long call, because the flag that
guards a direct call is set when the callee is attached, and the callee is attached at its *first call* (decision 3): the first guard failed, typed code
handed over, and the rest of the caller ran boxed with ordinary calls.  A failed guard now takes the stub that makes the ordinary call with boxed
arguments, and typed code continues with the result when it has the kind the callee's typed code returns (otherwise it hands over as before).  The
same continuation applies when a callee falls back to its boxed code.  Instructions per call: 3036 to 48 (56x the interpreter).

Calls that leave trailing arguments out are direct calls too when the omitted defaults are numbers (0.89x to 57.6x).  A call to a translated proc that needs a
frame (arrays, `global`, `variable`) cannot be a direct call; if the callee is *caller-safe* the interpreter makes the call and typed code goes on.  Caller-safe
means: no `upvar` to a level other than 0 or #0, no `uplevel`, `eval`, `expr` of a dynamic string, `tailcall` or `{*}` call, only built-ins that stay in
their own frame, only callees that are caller-safe themselves.  Such a callee cannot reach the caller's variables, so they can stay in C variables.
Known limit: a variable trace handler of a variable the callee touches that itself reaches two frames up (`uplevel 2`) would see stale caller variables;
nothing else can.  A call to a tiny callee of this kind costs the interpreter's call plus the entry into compiled code (about 850 instructions) and measures
0.82x; its value is that the caller's loop stays typed.

## 15. Math functions

Calls of `tcl::mathfunc::*` (`sqrt`, `int`, `double`, `abs`, `round`, `floor`, `ceil`, `pow`, `sin`, ...) ended typed code, so any numeric loop using one ran
boxed after it: 1.2x the interpreter.  They are computed in C now, with the conversions and result checks of Tcl's own implementations (NaN, and `errno`
other than a range error with a zero or infinite result, make the step start again in the boxed code, which raises Tcl's error).  `floor` and `ceil` of an
integer above 2^53 differ between a C cast (rounds) and Tcl's bignum path (truncates), so those are left to Tcl; found by the differential test.  The
rest (`bool`, `entier`, `isqrt`, `rand`, `srand`) are ordinary calls of a built-in that runs in typed code; `max` and `min` are procs of the Tcl library
and stay as they were.  Loops: 332 M to 5.3 M instructions (62x) and 221 M to 3.1 M (70x).

A compiler can also get in the way: clang for wasm32 turned `asin` of an integer into an intrinsic and, knowing the argument was no NaN, folded the
`r == r` test away, so `asin(2)` came back as a NaN result instead of an error.  The wasm32 guest run of the differential test found it (30 calls).  The
results of the libm calls now go through a volatile object before they are tested (`tbc_opaque_dbl`).  The suite also passes with clang as the native compiler.

This is right only while the commands are Tcl's own.  A flag says so; it is cleared when one of them is renamed or deleted (command traces), when a
proc is defined under a name that contains `::tcl::mathfunc::`, and it starts out cleared if a namespace other than the global one already has a
`tcl::mathfunc` child with commands.  When it is clear, typed code hands over to boxed code at the call.  It is never set again in that process.

## 16. More of the instruction set in typed code

* The instructions the executor implements by calling a command that uses no variable (`string index/first/last/range/replace/trim*/match/toupper/...`,
  `regexp`, `lrange` and `lindex` with indices, `in`/`ni`) are done with boxed operands in typed code (the table is shared with boxed code).
  `eq`, `ne` and `string compare` do the comparison directly (two integers: a machine comparison), `**` calls the runtime's boxed operator, `concat`
  and the stack-copying `over` are taken.  A `string length` / `string first` loop: 0.88x to 1.40x.
* `foreach`: the lists are held as objects, the iteration state in two C variables; when typed code hands over, the interpreter's iteration object is rebuilt from
  them.  Loop variables are objects (or frame variables).  5.5x the interpreter on a loop summing 1000 elements.
* `catch`: `beginCatch` and `endCatch` change nothing in typed code.  A failure inside the body hands over to boxed code at that instruction, and the
  boxed code dispatches to the handler.  1.56x to 14.3x on a loop with a catch.
* `switch` with a jump table: an integer key is a C `switch` over the keys written as canonical integers (the key's text is the integer's canonical
  form, so no other key can match it); any other key is compared with the literal keys as the boxed code does.  1.36x to 33x.
* `incr` of a local that holds an object (a loop variable, a list element), `llength` of a number, `string map` and the concatenation of two lists.
* The hint file (`-hints`) matched bare proc names against the translator's fully qualified ones and so never took effect; the signatures it lists
  (`D`, `DD`, ...) were not generated.  Fixed; the differential test now enters those variants as well.

Census of the instructions at which typed code still gives up, over 694 procs from tcllib packages: before these changes 1603 sites (`invokeStk` 704,
`foreach_start` 205, `returnImm` 199, ...), now 1545 of which `foreach_start` and `jumpTable` are gone and `invokeStk` is 530: calls of `upvar` as a command (76),
`package` (36), `lsort` (27), `array names` (18), `rename` (16), `regsub` (16), `binary scan` (14), `uplevel` (13), `regexp`, file and channel commands.  `returnImm` is
`return -code`, which ends the proc anyway.

Not taken yet, and listed with `TBC_DEADOPS=1`: `dict for`, `lmap`, `unset`, `info exists` of a plain local, `array exists`, `append`/`lappend` on a frame
variable, `lsort`, commands that name variables (`array names`, `uplevel`, `upvar` as a command, `regexp` with variable names), and commands that are not
known to leave the caller's variables alone.

## 17. Local arrays held natively, and two fixes found on the way

An array that is a compiled local, is not an argument, and is touched only by element loads, stores, increments and `info exists` (nothing else names it in the
bytecode: no `unset`, `append`, `lappend`, `array exists`, `upvar`, ...) cannot be seen by anything else while typed code runs: the callees typed code calls
are caller-safe, and every command that could reach it by name is one at which typed code hands over anyway.  Typed code therefore keeps such an array (kind R)
in a table of its own: elements are `Tcl_Obj` values keyed by their text, in the order they were made.  When typed code hands over, the elements are written
into the frame in that order, so the hash table the boxed code goes on with is the one the interpreter would have built (the order `array names` lists them in
depends on it).  A read of an element that is not there, an increment of a value that is not an integer or that overflows, and any other failure hand over
the same way, so the boxed code raises the interpreter's error.  Such procs no longer need a frame, so a typed caller calls them directly.

Measured as instruction counts, interpreter / compiled: array sieve 2.1x to 4.5x, array histogram 5.2x to 7.4x, array Fibonacci 1.8x to 3.3x, a loop calling a
tiny proc that uses an array of its own 0.8x to 2.4x.  The matrix product over `$i,$j` keys moved from 1.7x to 1.8x only: its time is in building the key.

What bounds it: a proc call that needs a frame costs the interpreter's own call (frame, argument binding, the stub bytecode and its second dispatch, about 900
instructions more than the interpreter); the array in that benchmark was most of the rest.  With the array gone the call is direct.

Found by checking this against the interpreter:

* A proc with no frame variables that called a proc with effects (one that needs a frame) could, on a later failure, start the whole call over in the boxed code,
  and so repeat the callee's effects (a counter incremented twice).  Such procs now resume at the failing instruction, as procs with frame variables do.
  `tfx_eff` in the differential test.
* The boxed code's `info exists a(k)` looked the element up the way the interpreter does when a read trace has to run (make an entry, then remove it again).
  The interpreter takes a shortcut that makes no entry unless a trace is involved.  The entry made and removed again changes when the hash table grows and so the
  order in which `array names` lists the elements.  Fixed; `tr_exists_order` in the differential test, and a `fr_` family in the typed fuzzer (random programs
  over local arrays, including ones that fail halfway and write the table out, 64000 calls per seed, seeds 1 to 8 clean).

## 18. Handing over at every instruction

Typed code can leave typed mode at any instruction (an assumption fails, a tick is due, the instruction is not implemented).  The ways out were tested by the
programs that happen to fail there, which left most instruction/state combinations untested.  A module translated with `TBC_FORCE_DEOPT=1` now asks, at every
typed instruction, whether to hand over (`TBC_FORCE_RATE=n`: about one instruction in n, from a seeded generator), and the differential test and the typed fuzzer run
that way (`tests/run.sh`).  It found one bug at once: the loop variables of `foreach` were not written to the frame when typed code handed over inside or right
after the loop, because the liveness analysis took `foreach_step` for a definition that always happens, while at the end of the list the variables keep their
values (`foreach x $l {}; info exists x` answered no).  Fixed (`tf_after`, `tfe_after`).  18 combinations of rate and seed are clean on the differential test.

A hand-over in the middle of a pure recursion enters the next body from the interpreter, so the recursion-limit edge is the one of decision 4 (one level early);
the forced run compares those checks with the tolerance used for the other procs.

## 19. Built-ins the analysis relied on can be replaced

Purity and caller-safety rest on facts about commands: `lreverse` runs no script and cannot touch the caller's variables, so typed code keeps the caller's
variables in C locals across a call of it.  A program can break that after the module is compiled: `rename lreverse x; proc lreverse {l} { uplevel 1 {set x 77} ... }`
made the compiled proc answer with a stale `x` where the interpreter answers 77 (found by looking for divergences by hand; the tests had never replaced a built-in).
Math functions had a guard for this (`tbc_mf_ok`); the other built-ins had none.

The translator lists, for every proc, the built-ins it relied on, with the namespace each is looked up from (and those of every proc it calls).  The module
registers them.  The check is Tcl's own: a cached command name stays valid only while the command's epoch, the namespace and the namespace's `cmdRefEpoch`
(and `resolverEpoch`) are unchanged.  At load the global built-in is pinned (reference held, epoch noted).  At each entry of a proc with such dependencies the
module compares the namespace's `nsId`, `cmdRefEpoch` and `resolverEpoch` and the pinned command's `cmdEpoch` and `CMD_IS_DELETED` with what was last verified;
a few compares, and nothing else, while nothing has changed.  When one differs the names are looked up again from the namespace (`Tcl_FindCommand`), and a
dependency that no longer gives the pinned command (or an import of it) is withdrawn for good; an entry with a withdrawn dependency runs the interpreter's
version.  Withdrawal is for good because the program may have put the original back and the epoch gives no way to tell a command that was replaced from one
that was replaced twice.  Covered, each with a check in `tb_*` / `tbal` / `tbim` that fails without the guard: rename, delete, `proc` in the global or a nested
namespace, `interp alias` into a nested namespace, `namespace import`, `interp hide`, and putting the original back.

The first design of this guard (a flag per name, withdrawn when any command *ending* in that name existed in any namespace) was wrong in the other direction:
Tcl's own `::tcl::binary::format`, `::tcl::clock::format`, `::tcl::file::join`, `::tcl::file::split` and `::tcl::chan::puts` made it withdraw `format`, `join`,
`split` and `puts`, so procs that used them ran interpreted (found profiling eleven tcllib-style workloads: 172 of 183 calls of the sha1 proc ran interpreted).
Resolving from the proc's namespace, as above, fixes it: the same workloads run 6-11% fewer instructions, and the report check `tb_fmt`/`tb_spl` fails when they
fall back again.

What the check does not do: it is made when a compiled proc is entered, not while it runs.  The interpreter resolves a name at every call.  Two procs that rename
and redefine a built-in they use between two calls of it (`tb_self`, `tb_self2`: the second also has the new command write the caller's variable) give the
interpreter's results in the differential test; that is all that has been shown.  There is no argument that it holds for every shape of body, so it is not
claimed.

*Closed by decision 50: the epoch test of the interpreter's own `INST_START_CMD` is made while a compiled proc runs, and the pinned built-ins are checked again after anything that can run a script.*

Checked: with the guard forced open the differential test fails; with it, the full `tests/run.sh` passes (differential 12951 calls, forced hand-over, fuzz typed
seeds 1-3 and boxed seeds 1-2, valgrind 12923 calls, 0 mismatches).

The first forced-hand-over fuzz run crashed.  The cause was in the test instrumentation: the coverage counters of a `-DTBC_COV` build (a fixed table of 8192 sites, no bound
check) overflowed once every instruction had a hand-over site, and wrote over `tbcOne`.  The table is larger now and the sites beyond it share the last slot.

## 20. Procs that yield

A coroutine is suspended by unwinding the interpreter's non-recursive stack, which cannot cross a C frame; Tcl answers a `yield` below one with "cannot yield: C
stack busy".  The boxed code of a proc is a function that can be entered at any instruction with the operand stack in an array, so it can suspend the way the
bytecode executor does it: at a `yield` it keeps the stack below the yielded value in a heap record, pushes a resume callback and Tcl's own
`TclNRCoroutineActivateCallback` on the interpreter's stack, and returns up to the interpreter's trampoline, which does the switch.  When the coroutine is
resumed the callback gets the record back and goes on in the boxed code at the next instruction with the resumer's value as the result of the `yield`.
A coroutine deleted while suspended rewinds: the callback releases the record and returns an error.  `yieldto` does the same after installing its tailcall.

* The proc must be entered by the interpreter, not by compiled code (a C frame of compiled code above it would prevent the switch), and everything else it runs
  must be yield-safe (decision 5); otherwise, inside a coroutine, the interpreter's version runs.
* A yield inside a `dict for` (the iteration state is in C variables) or inside a `{*}` expansion is refused (such procs stay interpreted).  Native arrays,
  lists and maps are not used in a proc that yields (they cannot be rebuilt from the frame).
* Typed code is entered again after a yield where it pays: the typed analysis keeps the state after each yield (`seed`), and the generic variant has a copy
  (`V_<proc>_RE`) that starts there.  It reads the locals that may have been assigned from the frame and checks them (an integer for an integer variable, no
  trace, no link, no array: the boxed code has run since the typed code handed over, so nothing can be assumed) and the stack slots; if anything is not as
  expected the boxed code goes on instead.  The copy is made only where a loop that contains no yield can be reached before the next one: the transition costs
  about 200 instructions, so a generator whose loop body is just the yield stays boxed.

Measured as instruction counts, interpreter / compiled: a generator that does nothing but yield 20000 times 1.03x (Tcl's own switch is about 4300 instructions
per yield and resume); one that computes in a loop of its own between yields 9x in total (20x without the start-up); one that computes in a helper proc 9x.

Found on the way, by the forced hand-over test: the table of boxed-code entry points was built the first time it was asked, in a function whose loop variable had
the name of its argument.  The first lookup of a translation therefore asked about the wrong instruction, and a hand-over at that instruction ran the `default`
of the entry switch: success with an empty result.  Fixed, the `default` is now an error, and the translator checks, after generating, that every entry the
generated code makes has a case.

## 21. Typed code on integers written as 0xFF, and on `binary scan` of numbers

Profiling eleven tcllib-style workloads (see decision 19) showed the checksum procs (sha1, md5, crc32) spending 33-48% of their instructions in the boxed
helpers for `&`, `^` and `>>`.  Two things kept typed code from running there.

* **Integer literals that are not written canonically** (`0xFF`, `0xFFFFFFFF`, `010`, `0b11`) were string literals to the translator, so an integer operation with one
  of them as an operand handed over to boxed code.  They are classified as strings for a reason (a `set x 0xFF` must keep its text), but an operand of an integer
  operation is only read.  `operandOf` now reads the value of such a literal (`string is wideinteger`, evaluated with `expr`, so octal and `0b` follow this Tcl).
  A literal outside 64 bits, or one that is a double, is still not an integer operand.  `tests/typed.sh` fails without this (a crc loop hands over at `bitand` and
  `bitxor`); the differential test has `tl_*` procs with hex, octal, binary, a leading space, out of range, and non-numbers.
  Measured on a crc loop over a list of 1000 ints: 0.51 s interpreted, 0.42 s compiled before, 0.11 s after (4.7x).
* **`binary scan $data <t>* var`** named a variable, so typed code (which has no frame) stopped there.  For one of `c s S i I` with an optional `u`, a count of `*`, a
  data operand that is an object or a literal, and a variable that is a local held as an object, the list is built in C (`tbc_bscan`: ScanNumber's byte order and sign
  extension, whole numbers only, no data gives the empty object, the same `Tcl_GetByteArrayFromObj` as the command) and stored like `set`; the result is 1.  Any
  other form runs the command as before.  The differential test covers every format and flag with data of 0..9 bytes, bytes of both signs, characters above 255,
  numbers, lists, an existing value in the variable, a variable that is an array, an array element, a variable format, and a call without the variable.
  `tcl::binary::scan` is also counted among the commands that stay in their own frame, so a proc that uses it can be called from typed code.
  What the inlined command does not do: count in `info cmdcount`, or run execution traces on `binary` (the same as the math functions in decision 15).

Measured on the tcllib procs, as instruction counts net of start-up, interpreter / compiled: sha1 544M / 317M (1.72x; 1.12x before), crc32 378M / 356M (1.06x),
md5 464M / 452M (1.03x), binary 1206M / 854M (1.41x; 0.99x as shipped before decision 19, 1.12x with only the guard relaxed; the share of this decision was not separated).

What is left in these three, and why it was not changed:
* **crc32** does not benefit.  tcllib sets `signbit` to 2^63, so `~$signbit>>7` is bignum arithmetic and typed code hands over at the first instruction of every call;
  the loop then runs boxed.  Typed code cannot do bignums.  What would help is entering typed code again from boxed code at a loop head (the machinery that resumes
  after a yield does this for coroutines).  Not built; see the roadmap.
* **md5** runs its transform in boxed code: `variable $token` and `upvar 0 $token state` name variables by a run-time string, and the state is an array.  It is as
  fast as the interpreter.
* The attribution of the rest is Tcl's own work: regexp/regsub 30-50% of the text workloads, object allocation 18-48%, with the thread-data lookup of a threaded Tcl build (`pthread_getspecific`) 10-28% of all instructions, and about 350 instructions to dispatch a command implemented in C.

Two defects of this change were found by the test stages that exist for this purpose, and fixed before it was released:
* The inlined `binary scan` writes its variable by name; the analysis that decides which locals a hand-over must write to the frame did not know that, so a
  hand-over right after the scan lost the list (`can't read "v": no such variable`).  Found by the forced hand-over stage (`tbs_sum_*`).  The instruction now counts as
  a use and a definition of the local, and keeps it from being held as a native array.
* `string is wideinteger` accepts integers beyond 64 bits.  A constant folded by Tcl's compiler (`9223372036854775807 + 2147483648`) was read as an int64 operand and
  gave a wrong answer.  Found by fuzz typed seed 3 with forced hand-over (`fz_11`).  The range is now checked; `tl_lit_fold` and `tl_lit_big2` fail without it.

Checked: the full `tests/run.sh` passes on this tree (differential 13460 calls in four modes, forced hand-over 6 configurations, fuzz typed seeds 1-3 and boxed seeds
1-2, valgrind 13431 calls, 0 mismatches).

## 22. What was measured for native aggregates, hash growth and lazy strings

Asked for: native doubles and strings, native aggregates passed between compiled procs, strings built lazily, incremental growth and presizing of the hash
tables the generated code owns.  Measured on this tree, as instruction counts (valgrind, start-up included, so small figures are inflated by it):

* **Doubles** are already native in typed code (kind D), through calls, math functions and `foreach`; nothing is boxed between operations.
* **Hash growth.**  A native counting map (`dict incr` on 100003 distinct keys, 400000 increments) runs 398.2M instructions with the map growing by doubling from 16
  entries, and 394.6M when it starts at the final size: 1.7% of the work net of start-up, which is the most that presizing from a compile-time hint could give, and
  it would cost 2 MB per map that never grows.  Not changed.  A single doubling at 65k entries re-inserts 65k entries (about 0.5M instructions), so there is no
  latency spike worth removing either.
* **Native aggregates between compiled procs.**  A proc that builds a 1000-element native vector and calls a helper with it 2000 times: 1257M interpreted, 180M
  compiled, against 44M when the helper's loop is written inline.  The call hands over to boxed code (a native vector cannot be an argument), so the helper gets

  array directly (what `Tcl_ListObjGetElements` does for a list) instead of calling it; the helper above went from 180M to 142M (21%).
* **Strings built lazily.**  Decision 10 measured typed strings: generated code is 0-7% of the string workloads, the rest is Tcl's own commands.  The profile of
  the eleven workloads agrees: generated code is 0.7-8.5% of the six text workloads, and the string-object work in them (2-23%) is done by Tcl's own functions,
  which lazy building in generated code would not remove.  Nothing was built.

## 23. Boxed code enters typed code again at a loop head

When typed code hands over (a bignum operand, a value of the wrong kind), the rest of that call used to run boxed, however hot the loop that followed.  tcllib's
crc32 did this on every call (`signbit` is 2^63, so `~$signbit>>7` is bignum arithmetic): 1.06x the interpreter, against 4.7x for the same byte loop when typed.

Now the boxed code of a proc that has typed variants, at the head of an outermost loop that typed code knows the state at, calls the typed variant for boxed
arguments with a resume point (the instruction, and the operand stack, in thread-wide variables the variant reads and clears first thing).  The variant reads the locals
that may have been assigned from the frame and checks them as the entry after a yield does (decision 20): an integer for an integer variable, no trace, no link, no
array; a variable the typed code keeps in the frame must not be linked to a variable of this very frame; each stack slot is of its kind.  If anything does not fit,
the boxed code goes on instead.  If it fits, typed code runs to the end of the call.  Entering is attempted once per activation of the boxed code, and a variant that was entered
this way hands over to boxed code that does not try again (`tbc_noosr`, set at every hand-over from it), so a loop whose typed code keeps giving up costs two
transitions, not one per iteration.  The failure labels of that variant resume at the failing instruction (the call cannot be started over: the boxed code has run).

Design choice, measured.  The first version was a separate copy of the typed variant that starts at the loop heads (as for yield): +17-18% machine code and +19-29%
compile time on the benchmark procs and on tcllib's sha1 module.  Entering the shared variant costs +1.1% machine code and +4% compile time on the sha1 module
(+8.8% on the benchmark file, whose procs are a few lines each, so the fixed part per proc dominates).  Only outermost loop heads are entry points.

Results, instruction counts net of start-up, interpreter / compiled: crc32 378M / 154M (2.45x; 1.06x before).  The other ten workloads of decision 21's table are
unchanged (sha1 1.74x, md5 1.03x, base64 0.99x, json 0.98x, csv 0.96x, structlist 0.99x, textutil 1.04x, tokenizer 0.97x, records 1.05x, binary 1.41x).

Tests: `os_*` procs hand over before a loop (a bignum), in the middle of one, give up the entry, nest loops, `foreach`, `while` with `break`/`continue`, raise an error
in the loop, `catch` inside it, `return` from it, use doubles, and take their arguments as numbers or text; the differential test compares them with the interpreter.
`tests/osr.sh` fails unless each of them did enter typed code again (coverage counters), which equal results alone would not show.

Two defects found on the way, both fixed:
* The first version restarted the whole call when typed code failed after an entry (the failure chains of a proc without frame variables do that); the boxed code had
  already run, and the error info showed `tbc: restart in a resumed body`.  The variant now resumes at the failing instruction.
* The entry after a yield (decision 20) skipped the variables typed code keeps in the frame.  A proc that links a variable to one of its own (`upvar 0 y x`) after
  typed code has handed over, and then yields, returned a stale value for `y` when typed code was entered again: `ty_same` fails without the check.  The check is now
  made by both entries.

Checked: the full `tests/run.sh` passes on this tree (differential 13591 calls in four modes, forced hand-over 6 configurations, `tests/osr.sh`, `tests/typed.sh`, fuzz typed
seeds 1-3 and boxed seeds 1-2, valgrind 13552 calls, 0 mismatches).  The earlier commit of this change (80406ea) was a work-in-progress snapshot made while that run was
pending.

## 24. Two things that were measured or reasoned about and not built

* **Eliminating the overflow check of integer additions** (for example `incr i` in a counting loop).  Upper bound: every `__builtin_add_overflow` in the generated code of
  the benchmark file replaced by a plain add, timed with the same module: `int_loop` 16.2 ms to 15.6 ms, `arr_sieve` 70.2 ms to 68.0 ms, the others within noise.
  At most 0-4%; the analysis that proves a counter cannot overflow would be code that can be wrong for that gain.
* **Calling the C procedure of a pure built-in directly** (`string first`, `lrange`, ...) instead of through the interpreter's command dispatch (about 350 instructions
  per call).  It would cut the dispatch share (estimated 1.6-7% of the eleven workloads, up to 2x on a loop that does nothing but call such commands, `str_ops`
  1.45x).  It changes what a program can observe: `info cmdcount` would not count the call, execution traces and `interp limit command` would not see it, and the
  interpreter's checks between commands would be skipped, unless the call repeated each of them (which is most of the dispatch cost).  Not done.

## 25. Keys such as `$i,$j` for native arrays are built as text, not as objects

A proc that works on `a($i,$j)` keeps the array in a table of its own (kind R, decision 17), but each key was built as a Tcl string object (`tbc_cat_*`), used for one
lookup and freed: about 800 instructions per key, most of it allocation.  `arr_mat` (a 40x40 matrix product) ran 1.8x the interpreter.

A `strcat` whose parts are integers and literals now leaves its result in a buffer of the stack slot (kind K: text in `kb<slot>`, its length in `kl<slot>`, at most 100
bytes by construction: an integer is at most 20 characters), when the instruction that uses the key is an element operation on a native array (load, store, `incr`,
`info exists`) that follows with only simple instructions between (`keyConsumer`).  The array operations take the bytes from the buffer.  Anywhere else the key is
needed as an object (a hand-over, a join with a path that has an object, a store into a variable) the object is made then (`boxe`), so every other path behaves as
before; a key with a text part (a variable that holds a string) is not made a K and goes the old way.

Measured, instruction counts net of start-up, interpreter / compiled: `arr_mat` 189M / 38M (5.0x; 1.8x before); `arr_sieve` 4.6x, `arr_hist` 7.5x, `nn::fill` 2.1x,
unchanged by this change (the last is a namespace array, which stays in Tcl's table: roadmap).

Tests: `mk_*` procs build keys of two and three integers, with negative and 64-bit values, with literal prefixes and suffixes, with a bignum stored under the key
(a hand-over right after the key was built), with a text part, and with a lookup that fails; the forced hand-over stage hands over at every instruction of them.
`tests/typed.sh` fails if a proc of that shape builds a Tcl object for the key.

## 26. Typed code after `variable $name` / `upvar 0 $name x`, and integer variables read from arrays and lists

tcllib's md5 ran 1.03x the interpreter.  Its transform starts with `variable $token` and `upvar 0 $token state`, and the typed analysis stopped at the first
(`variable` with a name held in a variable is an ordinary command call, which typed code does not make).  Everything after it, a loop of 64 steps per block, ran boxed.
Two changes, each general.

* **Typed code is analysed after such an instruction too.**  After a call of `variable`, `upvar` or `global` that typed code hands over at (the commands that link
  variables of the frame, by name), the typed state of the next instruction is a seed (as after a yield, decision 20): the stack slots below as they were, the result as
  an object.  It is done only where a loop head can be reached from there; the boxed code runs the call and goes on until the loop head, where it enters typed code
  again (decision 23).  The checks of that entry make the assumptions safe: the locals are read from the frame and checked against the kinds typed code expects.
* **Integer variables that are assigned objects.**  `set A $state(A)` stored an object, `set A [expr {...}]` an integer, so `A` was an object variable and every
  assignment of an integer allocated one.  A variable that an instruction uses as a number (a load whose next user is arithmetic, a comparison or a bit operation) and that is
  assigned a value loaded from an array or a list straight before the store, as well as integers, is now held as an integer; the store checks the value
  (`tbc_arg_int`) and hands over to the boxed code, which does the store, if it is anything else (a double, text, a bignum).  A variable that is only ever assigned
  loaded values stays an object variable, so text that passes through a loop is not checked.

Measured, instruction counts net of start-up, interpreter / compiled: md5 464M / 104M (4.45x; 1.03x before); sha1 544M / 313M (1.74x, unchanged).  Variable kinds of
the 608 proc variants in the tests, the benchmarks and the eleven workloads, before and after: 599 the same, 9 with more integer variables, none with fewer.

Tests: `dn_up` (state through `upvar #0 $name`), `dnns::f` (`variable $token`, `upvar 0 $token`, `foreach` with several variables), `dn_list` (numbers from `lindex`), with
integers, zero, negative numbers, doubles, text, an empty value, a bignum, hex and octal text and a missing variable; `tests/osr.sh` fails unless each of them went on in typed
code, and the coverage counters show the check at the store failing for the values that are not integers.

## 27. Small arrays of a proc live in the proc's C frame; what was measured for calls from boxed code and for a Tcl without threads

* **Native arrays of up to four elements need no allocation.**  A proc that keeps an array for its own use (kind R, decision 17) allocated an element table (768 bytes) and a
  hash table (128 bytes) on the first store and freed them at the end of every call: 45% of the instructions of `call_frame` (a loop that calls a proc that fills and reads
  a one-element array) were malloc and free.  The first four elements, and a table for them, are now in the array's own storage, which is a local of the typed function; a fifth
  element moves the table to the heap with room for 16.  `call_frame`: 4.3x (2.4x before).  The tests that use native arrays (the `fa_`/`fx_` fuzz families, the `t*_arr`
  procs, `mk_*`) cover it; the fuzz and the forced hand-over stage pass.
* **Calls from boxed code to compiled procs** go through the interpreter's dispatch (about 500 instructions per call).  Calling the typed variant directly from boxed code
  would remove part of that.  The estimate of the share of proc calls in the eleven workloads is at most 6.3% (md5, before decision 26 made its calls typed to typed), 5.9%
  (records) and 2.2% (structlist), so at most about 3% could be saved; it would also skip what the dispatch does (`info cmdcount`, traces).  Not built.
* **A Tcl built without thread support** uses fewer instructions for the same work, because object allocation does not look up thread data (`pthread_getspecific` was 10-28% of
  the instructions of the workloads).  Measured with `--disable-threads` on two workloads, net of start-up: sha1 482.8M instead of 544.4M interpreted and 249.0M instead

  `TCL_OBJ`); a program that uses Tcl threads needs the threaded one.  Nothing in this repository changes.
* **Namespace arrays** (`nn::fill`): 2.1x counted in instructions of one cold run, 3.9x in wall time of the best of five; the README and the roadmap said 2.1x only.

## 28. Text and data: calls of built-ins, one-byte strings, `== {}`, and what the census of tcllib modules found

Asked for: every text and data optimisation that has no downside.  What was built, what was measured, what was left.

* **Calling a built-in's C procedure without the interpreter's dispatch.**  Measured on `string first o $s`: 943 instructions through `Tcl_EvalObjv`, 454 calling the procedure.
  Two places made such calls.
  - The executor's own instructions for `string first/last/index/range/trim/match/...`, `lrange` and `regexp` (cmdOpSpec): typed and boxed code called the command by name
    each time.  Each call site now pins the command the first time it runs and calls its procedure while the command is that one (not deleted, epoch unchanged, not a Tcl
    proc, not an NR command); anything else, and every error, is the dispatch by name as before.  In this Tcl a replaced `string first` is honoured by the interpreter (it
    recompiles), and the by-name fallback does the same (`pj_str` in the differential test replaces it and puts it back).
  - A call of a pure built-in as a command (`join`, `split`, `format`, `lreplace`, `lsearch`, ...) from typed code.  The module pins the commands of its guard
    (decision 19) and calls the procedure when nothing the dispatch does could matter: interpreter deleted, script cancelled or unwinding, async handler pending, a command
    limit set, the nesting limit reached, execution traces on the command or the interpreter, the command deleted, a proc or an NR command.  Otherwise, and on an error, the
    call is made through the interpreter (the commands are pure).  The command count is kept.  The test makes the trace, limit and replacement cases (`pj_*`) and fails
    when the trace check is removed.  Measured on a loop of `format`, `lreplace`, `lsearch`: 1.01x the interpreter before, 1.18x now.
* **`string first`, `last`, `index`, `range` on one-byte characters** are done in place (`tbc_s_first` and the others) when every operand is a plain string whose character
  count equals its byte count (O(1) once Tcl has counted them, as the command does); numbers, lists, byte arrays, non-ASCII text, an empty needle, and an index outside the
  32-bit range (Tcl raises an error for it) go to the command.  The result of `first` and `last` stays an unboxed integer in typed code.  The differential test has 1200 calls
  over ASCII, non-ASCII, NUL, byte arrays, numbers, lists and every index form (`sf_*`), and found the index range on the first run.  `str_ops` (bench): 112M instructions for
  100000 iterations before this work, 83M with the pinned call, 38M with the in-place path.
* **`$x == {}` and `$x != ""`** handed over to boxed code at the comparison (the empty string is not a number, so it was not an operand of an integer comparison).  The operands
  are compared as strings, so a number held unboxed is never equal to it and any other value is when its string form is empty.  This is the most common comparison in library
  code; `math::statistics::BasicStats` handed over at it.  `tests/typed.sh` fails without it.
* **Census of eleven more tcllib modules** (instruction counts net of start-up, interpreter / compiled, results equal): md4 5.5x, rc4 3.3x, blowfish 2.7x, numtheory 2.0x,
  soundex 1.23x, math::statistics 1.14x, math::linearalgebra 1.02x, base32 1.00x, yaml 0.97x.  The earlier census had numtheory at 0.75x and statistics at 0.91x.
* **Not built, and why.**
  - Floating-point data in lists.  Typed code treats an object operand of an arithmetic instruction as an integer and hands over when it is not one; for a list of floating-point
    numbers (`math::statistics`, `math::linearalgebra`) that is the first addition of the first call, and the rest runs boxed.  The fix is a number kind that carries its own
    tag (integer or double) through expressions and variables; it touches every arithmetic instruction, the variable kinds and the conversions at every boundary.  It is the next
    item on the roadmap, with this census as its measure.
  - `lsort -command` with a compiled comparator.  The interpreter evaluates the comparator as a script for each comparison; routing it to the compiled procedure needs a command of
    ours to stand in for the proc in the script (which shows in the error info of a failing comparator) or a copy of Tcl's merge sort.  Not built: the error text would differ.
  - A native regexp matcher for literal patterns.  In the tokenizer workload `miss` and `getVacantSS`, the construction of states of Tcl's matcher, are 27.5% of all
    instructions: its state cache is built again for every match.  It cannot be kept between matches without changing Tcl's matcher.  A matcher of our own, for a subset of
    patterns (classes, anchors, greedy quantifiers, no back references), would remove it, but its results (leftmost-longest rules, `-all`, `-inline`, `-indices`, `-start`,
    captures, `-nocase`) must equal Tcl's exactly, and the patterns of the library are mostly built at run time (the JSON tokenizer's is assembled when the package loads),
    which a translation-time matcher cannot see.  That is an engine, not an optimisation; it is not started, and the differential and fuzz setup here is what it would be tested with.
  - `string map`, `string match`, `split` with literal arguments: the dispatch part of their cost went with the pinned call above; what is left is the work of the commands.

## 29. Numbers that are integers or doubles at run time: the tagged kind W

Decision 28 left floating-point lists open: typed code took an object operand of an arithmetic instruction to be an integer and handed over when it was not, which for a list of
doubles was the first addition of the first call (`math::statistics::BasicStats`, `math::linearalgebra`).  A result that is an integer or a double depending on the data cannot be
given a kind in advance, so there is now a kind that carries its tag.

* **W** is a number with a tag: in a stack slot (`sw<p>` the tag, `si<p>` the integer, `sd<p>` the double), in a local variable (`wt<v>`, `i<v>`, `d<v>`).  `+ - * /` of numbers of any
  kinds give a W (integers by the integer rule with the same overflow and zero-divisor hand-overs, anything with a double by the double rule), `%` and the comparisons give an
  integer (a mixed comparison hands over for an integer a double does not hold exactly, as before).  An object operand is loaded as a W (an integer or a finite double; text,
  bignums and NaN hand over).  Unary `-`, `+`, `!`, truth tests, `dup`, `pop`, stores, loads, `incr` and returns take W.  A variable that is assigned integers and doubles, or a W,
  is a W variable (before it was an object variable, with an allocation at every assignment).  `sqrt`, `sin`, `double`, ... take a W operand directly.
* **Everything else takes W as an object.**  The state that goes into an instruction that does not take tagged numbers has its W slots boxed on the edge into it, so the
  instructions that do not know W (list and string operations, calls, ...) are unchanged; a hand-over boxes W like any other slot.  A W that is stored into a typed variable
  from an object must come back as it was, so it is accepted only in the forms the integer kind accepts (a canonical integer, a double without a string form of its own).
* **Policy.**  Integer code must not pay for tags, so W is used only in a proc with a sign of floating-point numbers: a double literal or a call of `double`, `sqrt`, `sin`, ...,
  `floor`, `ceil`.  Everything else is as before (the integer checksums are unchanged: sha1 1.75x, md5 4.55x, crc32 2.51x).  `TBC_FORCE_WPOLICY=1` makes the translator use W in every
  proc; the whole test suite runs that way as well, which is how the kind was tested.  Procs that yield do not use it.

## 30. Procs with no sign of floating-point numbers: an adaptive tagged version, and a defect in decision 29's boxing

Decision 29 used W only where the proc itself shows floating-point numbers.  A proc that only adds, multiplies or compares values that arrive as objects (`proc sum {l} {...foreach v $l {incr...}}`
over a list of doubles) kept the integer assumption: the first double handed over and the rest ran boxed.  Choosing by the data needs both versions of the proc, and growth had to stay small.

* **Eligibility** (`PI($P,wadapt)`): the proc has a loop, no bit operation or `%`, does not yield, and either accumulates (`set s [expr {$s + ...}]`, `incr` of a float-looking operand) or
  does arithmetic on a `foreach` variable.  Counting loops (`for {set i 0} ...`, `incr s $i`) and checksums are not eligible.  `TBC_FORCE_WPOLICY=1` still means W in every proc.
* **Mechanism.**  The proc gets one more variant, key suffix `w` (`P/Bw`), whose locals are W.  A flag `tbc_wp_<proc>` is set by the integer variants' guard (`tbc_wnote`) the first time an
  object operand is a finite double.  While the flag is set a call enters the boxed code, which re-enters the `w` variant at the first loop head (decision 21's re-entry; the `w` variant is
  pruned to what is reachable from loop heads), and typed callers that would call the integer variant take the generic call instead.  A proc that never meets a double never sets the flag and
  runs as before.
* **Defect found while measuring this.**  `wnorm`, which boxes the W slots going into an instruction that does not take tagged numbers, compared the *pc* of the next instruction with a list of
  opcode names, so it never recognised the instructions that do take them, and boxed every W slot on every edge: two double objects per loop iteration in all W code, floating-point procs
  included.  The first measurement of the adaptive version showed no gain for this reason (1.13x, against 1.27x without it, at 10 calls of the workload).  After the fix the same workload (four
  list-of-doubles procs, no float literal in them) goes from 1.52x to 3.26x.  `tests/typed.sh` counts the boxings in a W loop; it reports 7 where 2 are expected without the fix.
* **A second defect it exposed.**  With W slots staying unboxed over unary plus, the forced hand-over test (a hand-over just before `+$v`) reached the generic code's unary plus, which left the
  operand as it was: `+7.90` gave `7.90`, where Tcl's INST_UPLUS discards the string form of a number and gives `7.9` (`+0x10` is `16`).  `tbc_un` now does the same.  The forced hand-over stage
  failed (`wf_neg`, at every rate and seed it was run with) before the fix and passes after.
* **Measured** (instruction counts net of start-up, interpreter / compiled, results equal), against the tree of decision 29: `math::statistics` 1.84x to 6.20x, `math::linearalgebra` 1.38x to
  4.73x, `math::numtheory` 2.04x to 2.97x; the eleven workloads of decision 19 and the other seven census modules unchanged (compiled instruction counts within 0.03%).  Generated code: bench
  +0.7%, json, sha1, records 0%, linalg about +4%, `struct::list` about +12% (text size, measured before the boxing fix above; the run time of `struct::list` is unchanged).

Tests: `wa_*` procs (sums, means, dot products, maxima, polynomials, nested calls over lists of integers, doubles and mixed values, run with the default and forced policy; first calls enter the
integer variant, later calls the `w` variant: `tests/coverage.sh` shows `V:::wa_sum/B` and `V:::wa_sum/Bw/RE`); `tests/typed.sh` checks that `/Bw` exists for an accumulating proc and not for a bit-operation
or counting proc, and that W is not boxed inside a loop.  Full suite with the default and with the forced policy (see below).

## 31. Reports on how well compiled code does: `TBC_REPORT=1` and `tbc::hot`

Until now there were three ways to see what typed code does not cover, none of them complete: `tbc::report` (which procs run compiled), `TBC_DEADOPS=1` (the instructions typed code has no code for) and
the `-DTBC_COV` counters of the test suite (a flat list of names and counts that only the tests read, and only in a single-file build).  Neither said how much of a proc is typed code, nor
which instruction made typed code hand over most often at run time.

* **At translation, `TBC_REPORT=1`**: one line per variant of every proc (instructions, how many have typed code, how many can hand over when a check fails, how many have no typed code at all,
  the kinds of the locals and of the result) and, for every unsupported instruction, its name, the command it calls and its position.  The count of unsupported instructions equals what
  `TBC_DEADOPS=1` lists (checked on three procs).  A variant's percentage is of the instructions the proc can reach: what follows an unsupported instruction runs boxed, so it is lower there.
* **At run time, `tbc::hot ?-top n? ?-dict? ?-reset?`**, in a module built with `-DTBC_COV` (a measuring build; without the flag the command does not exist and the macros are empty, so
  normal builds are unchanged).  Per proc: entries of typed code by variant, entries again at a loop head from the boxed code, hand-overs at an instruction, after a call, and the instructions
  it handed over at most often, with their command and a kind: `unsupported` (no typed code for the instruction: it hands over every time) or `guard` (a check failed).  The sites carry their
  description from the translator (`TBC_HITI`); the counter names the tests match are unchanged.  The table of counters is now part of the shared state, so a split module counts too (it

## 32. Comparisons of objects that are not integers stay in typed code

`tbc::hot` (decision 31) over the 21 workloads of decisions 19 and 28 counted 168664 hand-overs at instructions, of which about 28% were comparisons: `eq`/`neq` of objects that are not integers

* **Change.**  A comparison (`< <= > >= == !=`) with an object operand, or with an operand that has no numeric kind (a text literal), takes the interpreter's rule through the same generic compare the boxed code

## 33. What the AOT covers in all of tcllib, where run time goes, and three defects the whole-library run found

**Correction to decision 32's closing remark.**  `upvar` and `uplevel` were 31% of the hand-over events of the 21 workloads (`upvar $name var` in `json::parseValue` and the `Pop` helpers, `uplevel` in `struct::list::FTest`,
`Lfold`, `Lmap`, `Lfilter`), and I took them for the next thing to examine.  Counting events overstates the cost: a hand-over early in a proc costs little, and what follows runs in the boxed code, which is what ran before
typed code existed.  What bounds the gain is the share of the run that is generated code at all.  Measured by callgrind (instructions net of start-up; self cost of the generated functions as a share of the compiled run):
base64 0.3%, json 1.0%, `struct::list` 1.1%, csv 2.0%, tokenizer 2.4%, yaml 2.7%, textutil 3.1%, binary 3.5%, records 3.6%, base32 0.0%, soundex 6.6%, sha1 7.5%, md5 8.3%, numtheory 10.8%, md4 11.8%, blowfish 14.0%,
crc32 14.4%, rc4 16.0%, `math::statistics` 34.2%, `math::linearalgebra` 40.9%.  The rest is Tcl: the regexp engine and list parsing in json, the allocator, hashing and script compilation in `struct::list` (where
`uplevel` evaluates a script, which the interpreter has to do either way).  Making `upvar` and `uplevel` typed could gain at most about 1% on those two; it is not worth the risk to the frame handling, and it is not planned.

**What it covers (measured).**  All of tcllib 1.21 (367 packages loaded; 57 would not load in the interpreter used) with 6840 procs, by the translator's census: 6837 translate (at least to boxed code), 3 are refused
(`cron::runTasksCoro`, `oo::Helpers::classvariable`, `oo::define::classmethod`: the TclOO instructions `tclooClass`, `tclooNamespace`, `tclooIsObject`).  Of Tcl 8.6.14's 190 bytecode instructions the translator has code for
177; the others are `lor`, `land`, `callBuiltinFunc1`, `callFunc1`, `foreach_start4`, `foreach_step4`, `dictDone` (not emitted by the 8.6 compiler for procs, except possibly `dictDone`, which was not looked for) and the
TclOO ones.  The typed share is much lower (static counts by the compile-time report of decision 31, over 6750 procs and 12258 variants, translated in 12 chunks of 600 procs, so a call from one chunk to a proc in another
does not have the callee's kinds): 27.3% of the reachable instructions are typed code (best variant of each proc), the median proc is 58% typed, 23.6% of the procs have no instruction typed code lacks (14.3% of the
4938 procs of 20 instructions or more).  The instructions typed code lacks in most procs: a call of a command whose name is not a literal (573 procs), `returnImm` (564), `uplevel` (291), `listIndexImm` (274),
`arrayExistsImm` (212), `upvar` (197), `currentNamespace` (160), `{*}` expansion (123).  These are counts of instructions in the code, not of what runs; typed code is entered again at loop heads, and most of tcllib is
not compute.

**Defect 1: translation time quadratic in the size of a proc.**  Translating the 12 chunks, one took 30 minutes (the others 20 to 40 seconds): `fileutil::magic::filetype::analyze`, a generated proc of 1.1 MB and 71037 lines.
Cause: finding the command of each instruction looped over all commands for every instruction (instructions times commands: 4.3 s for a table 1/16 the size of the one in the test).  It is now `cmdMap` (`src/cmdmap.tcl`),
which finds each command's first instruction by bisection.  The proc alone now translates in 67 s; the generated C is byte-identical to before on the test module, json, `struct::list`, statistics, md5 and blowfish.
A synthetic proc of 2000 statements: 69 s to 23 s.  Translation is still faster than linear in size but no longer quadratic in the instructions of this step: `analyze` (the typed analysis) grows 2.7 times per doubling of the
proc, and Tcl's own `::tcl::unsupported::getbytecode` (not ours to change) 3.3 times (3.1 s for 92000 instructions).  `tests/cmdmap.sh`: the result equals the old loop on 300 random nested tables, and 40000
instructions in 16000 commands are mapped in under 5 s (92 ms measured; the old loop takes about a minute on it).

**Defect 2: a program's proc with the name of one of the translator's own procs.**  The translator reads the program's file into its own interpreter, then defines its procs, so a global proc of the program named `lt`,
`kd`, `emit`, `analyze`, `operand`, `effect`, `refuse`... was replaced by the translator's before the module was written: the module held the translator's body and fingerprint for it, the proc was left to the
interpreter (`tbc::report`: "another definition of this name") and the translator said "5 of 5 procs compiled".  A proc named `allprocs` crashed the translator.  Now the helper that runs before the file is read is in a
namespace of its own, and the definitions (bytecode, body, arguments, defaults, fingerprint) of the procs that collide are read right after the file is, and `prepare` takes everything from that snapshot.  `tests/names.sh`
(ten such procs: compiled, results equal the interpreter's; failed on the previous translator) and a check that every fingerprint in the module of the test procs is a hexadecimal number.

**Defect 3: `TBC_REPORT` with a local variable named like a number** (`NaN`, `Inf`): `expr {... ? "#$v" : $vn}` read the name as a number and raised a domain error (`tests/hot.sh` now has such a proc; it failed
before).  The same pattern turned up in my first version of the fix for defect 2, where a fingerprint such as `53240e9073862955` went through `expr` and became `0xInf`: found by comparing the generated C with the previous
translator's, and by the suite's module build; a check for it is in `tests/names.sh`.

## 34. Dense native arrays, and the first measurement against C

**The goal and the first measurement against it.**  The aim is that unmodified Tcl compiles to code as fast as possible for any Tcl.  Every figure in the README is against the interpreter; nothing had been measured against C.
`bench/vs-c.sh` now does (the same eight kernels in Tcl and in C at `-O2`, wall time, best of three, results compared).  Before this decision, on four of them: integer loop 1.3x C, `fib(30)` 4.4x, sieve of 3M **250x**, 120x120
matrix product **134x**: a native array (kind R) was a hash table keyed by the text of the key, with a boxed object for every element, although the code that used it was entirely typed.

**Dense mode.**  An array a compiled proc keeps for itself (kind R) whose elements all have keys that are canonical non-negative integers (`0 ... 2147483647`; `01`, `+1`, ` 1`, `-1` are other keys), or all keys `i,j` of two such
integers, and were made in order without a gap, is a vector.  One-dimensional: keys `base, base+1, ...`.  Two-dimensional: the keys of a matrix filled row by row, the first row giving the width.  An integer element is held unboxed
(8 bytes beside a pointer for any other value, 16 bytes a slot); anything else, an element made out of order, a key of another form, turns the array into the table it was, the elements in the order they were made (which is the order
of the vector), so what typed code writes into the frame when it hands over, and the errors of absent elements, are what they were.  An array that was never used becomes dense with its first element.
* **Integer keys** reach elements without formatting the key as text (`tbc_r*_k`); a key `$i,$j` of two integers is carried as the two integers (stack kind `K:2`) and its text is only made if something needs it (`tbc_r*_k2`).
* **Element kinds.**  The translator tracks, per array, whether everything stored in it is an integer in canonical form (an integer register, a canonical integer literal): a load from such an array pushes an unboxed integer; a missing
  element, or one that is not an integer, hands over.  An integer literal is stored as the integer, not as the literal's object.
* **Measured** (wall time, compiled against C): sieve of 3M 1988 ms to 83 ms (C 7.6 ms, 10.9x); matrix product 107 ms to 9.8 ms (C 0.76 ms, 12.9x); the 21 workloads of decisions 19 and 28 are unchanged (compiled instruction
  counts within 0.1%, results equal).
* **The whole table** (`bench/vs-c.sh`, compiled / C): integer loop 1.3x, Collatz 1.7x, `fib(30)` 5.4x, sieve 10.9x, matrix product 12.9x, histogram 23x, array of doubles dot product 24x, longest common subsequence 129x.  What is
  left on arrays: 16 bytes a slot where C uses 1 to 8 (the sieve's 3M elements are 48 MB, C's 3 MB: a narrower vector that widens on demand); arrays of doubles are objects (element kind D); a histogram makes its keys out of order,
  so it stays the table; the LCS kernel computes its keys (`$d([expr {$i - 1}],$j)`) and calls `string index` in the loop.  These are the next steps, in this order of size.

Tests: `da_*` procs (ascending from 0, 1 and 5, descending, with a gap, strings, hex and `007` as values, negative and huge keys, keys `01`, `+3`, ` 4`, absent elements, `info exists`, `incr` of integers, of a string, at the
limit, matrices by row, by column, ragged, with a gap, with other keys, `$i, $j` with a space, 3-part keys; 277 more calls in the differential test, and the forced hand-over and forced tagged-number runs); `tests/hot.sh` counts the
conversions (`X:array dense ...` counters of a `-DTBC_COV` build): ascending 1-D and row-wise 2-D arrays stay dense, a descending one is turned into the table (this fails without dense mode); `tests/typed.sh`: the generated code
of a sieve and a matrix uses `tbc_rseti_k`, `tbc_rgetw_k`, `tbc_rseti_k2`, `tbc_rgetw_k2`.

Full-suite result: the whole of `tests/run.sh` from a snapshot of `cc95679`, exit 0 (16980 calls in the differential test in four modes, forced hand-over at three rates and two seeds, guard, typed, osr, hot, cmdmap, names,

## 35. Native arrays of doubles, in any order, with computed pair keys; the table against C after them

Decision 34 left four things on arrays; this decision does them (`bench/vs-c.sh`, compiled / C, wall time, best of three, results compared; the table of decision 34 in brackets):
integer loop 1.3x (1.3), Collatz 1.5x (1.7), `fib(30)` 5.1x (5.4), sieve 10.3x (10.9), matrix product **8.2x (12.9)**, histogram **2.9x (23)**, dot product of doubles **4.1x (24)**, longest common subsequence **31.8x (129)**.

* **Doubles and tagged numbers in a vector.**  A slot is an integer unboxed, a double unboxed (its bits, tag `TBC_RDBL`), or an object.  The element kind of an array is now I, D, W or B: D when only doubles are stored, W (a tagged number,
  decision 29) when integers and doubles are stored in a proc that uses tagged numbers, B otherwise.  A load from an array of kind D or W pushes an unboxed double or tagged number; a store of one stores it unboxed.  A double that
  an object holds is unboxed only if it has no string form of its own (as the interpreter's arithmetic makes them), an integer only in canonical form, so what comes back is the text it went in with.  Dot product of 1M doubles: 171 ms to 33 ms.
* **Pair keys with branches in the value.**  `set d($i,$j) [expr {$u > $l ? $u : $l}]` computes its value with jumps between the key and the store; the scan that finds where a key goes (`keyConsumer`) followed only straight-line code, so
  that key was built as an object.  It now follows every path from the key and requires that each ends at an array operation on a native array and none touches the slot (calls are passed, an argument expansion, `over`
  of the slot, `eval` are not).  The LCS recurrence of 600x600: 28 ms to 6 ms.
* **Integer keys in any order.**  A vector whose keys stop coming in order (a histogram, a descending fill, a random fill) is turned not into the table but into an unordered vector with holes and a list of the order the keys were made in
  (dmode 3, base 0), as long as the keys stay below four times the number of elements and at least 4096 (a key above that is the table's).  The elements are written into the frame in the order they were made, so `array names`
  and `array get` after a hand-over give what the interpreter's arrays give.  That order is observable: a proc that fills an array and then calls `array names` hands over at that call (listed by `TBC_REPORT`: 75 of the 6750 tcllib procs
  call it), and the array is still a native one up to there.  Histogram of 3M increments: 74 ms to 7.6 ms.
* **Fewer operations per element.**  The width of a row of a matrix is kept precomputed, the unboxed cases of the reads are the likely ones: the product kernel runs 56 instructions per inner iteration, not 72 (C: about 6).
* **What is left** (compiled / C): sieve 10.3x (16 bytes a slot where C uses 1: a narrower vector that widens on demand), matrix product 8.2x (the loop's own overhead, two lookups of about 14 instructions each, the check for
  asynchronous events at each loop head: caching the vector's fields in the loop would let the C compiler keep them in registers), LCS 31.8x (`string index` of two strings and a comparison in every cell), `fib` 5.1x (the call).

Tests: `da_dbl`, `da_dmix`, `da_dinf` (Inf, -Inf, -0.0, 0.1 + 0.2, 1e22, 1/3: the text of unboxed doubles), `da_dlit`, `da_dover` (an integer overwritten by a double and back), `da_dstr`, `da_dincr` (the error of `incr` of a double),

## 36. Lists of integers built by `lappend` are native vectors, and a defect in how literals keep their text

The next gap of decision 35 was lists.  A list that is built by `lappend`, does not escape the proc and holds integers is now a native vector (kind A, `tbc_ivec` = pointer, length, capacity), like the vectors of decision 12; before, every `lappend` boxed its
value and went through `Tcl_ListObjAppendElement`, and every `foreach` handed over.

* **Build.**  `set l {}` makes an empty vector, `lappend l $v` pushes (`tbc_ivec_push`; a failed allocation hands over at that instruction).  Whether a variable can be a vector is decided once per proc (`vecEligible`): the only instructions that may touch it are the ones typed code does on a vector (`lappend` whose result is dropped or returned, `lindex`, `llength`, `lset`, a `foreach` over it with one list and one variable, the return); a list that is passed to a command, joined, sorted or read by anything else stays a Tcl list, since a vector would only be turned back into one.
* **`foreach`.**  The loop copies the vector once (kind N, a snapshot: the body may append to the list, and the interpreter's loop does not see that), and the loop variable is an unboxed integer (I) where the body only uses it as one, a tagged number (W) or boxed (B) otherwise.  The variable's kind
  is found with two rounds of the liveness analysis because the loop variable's kind depends on the body, and the body's on the variable.
* **Measured** (`bench/vs-c.sh`, compiled / C, wall time, best of three, results compared; decision 35's first measurement in brackets): `lappend` + `lindex` sum **3.2x (34)**, `foreach` **11.7x (42)**; the other eleven kernels are unchanged
  (integer loop 1.2x, Collatz 1.6x, `fib` 4.4x, sieve 9.9x, matrix 8.2x, histogram 2.8x, doubles 4.3x, LCS 32.9x, `lset` 1.6x, `dict incr` 133x, string append 36x).
* **The defect.**  The new differential test procs found it: `lappend l 1e3` gave `1000.0` in compiled code (the interpreter keeps the text `1e3`).  It was not caused by the vectors; the committed translator did the same.  The compiler shares one literal object between the procs of an
  interpreter, so after any proc had used `1e3` as a number (`set a(1) 1e3` in an array of doubles), the object was a double *with* its text, and the translator took every double-typed literal object by value (`tbc_lit_d(1000.0)`), which loses the text.  A literal now keeps its text when the
  text reads back as the same number; it is taken by value only when it has no text (a folded constant) or its text does not read back as its value (Tcl's own text for 2^64, the case of `ta_fold_pow2c`: my first version of this fix broke it, and the differential test caught that).
  Check: `tests/typed.sh` translates `da_dlit`'s line and a proc that appends `1e3` and requires `tbc_lit("1e3", 3)`; the committed translator gives `tbc_lit_d(1000.0)` there.  `ls_hexlit` in the differential test (`0x10`, `007`, `1e3` appended to a list).
* **Tests.**  `ls_*` procs (`ls_sum`, `ls_for`, `ls_ret`, `ls_big`, `ls_break`, `ls_mod`, `ls_nest`, `ls_empty`, `ls_after`, `ls_idx`, `ls_lset`, `ls_lseterr`, `ls_reset`, `ls_mixed`, `ls_pass`, `ls_res`, `ls_hexlit`, `ls_two`, `ls_copy`, `ls_var`: lists that are built and read in different ways, copied then appended to, passed on, mixed with non-integers, a loop variable assigned in the body) and 17335 calls in the differential test in four modes, forced hand-over (three rates, two seeds), `TBC_FORCE_WPOLICY=1`;
  `tests/typed.sh` requires `tbc_ivec_push` for a `lappend` loop and no hand-over at `lappend`, `foreach` and the arithmetic of the loop.
* **Not done** (compiled / C, the next gaps): doubles in list vectors, where the 11.7x of the `foreach` kernel goes (not measured: the loop variable's kind and the snapshot copy are the candidates), `dict incr` with computed integer keys (133x), `append` with `string index` (36x).

## 37. `binary format` is a pure built-in, and execution traces on built-ins and their ensembles are the interpreter's

A fork of this work reported that adding `tcl::binary::format` to the built-ins that need no frame (`tbcPureBuiltins`) took a frame-building loop from 0.96x to 1.83x, tested on a copy with 18 cases.  This decision checks that with cases of its own, and records what the check found.

* **The speed.**  A proc that packs a header (`binary format SIa4 ...`) called 400000 times from a loop: interpreter 251-280 ms; compiled before the change 310 ms (**0.81x**); after it 117-120 ms (**2.2-2.3x**).  The fork's figures are for another benchmark.  Why it helps: a proc that uses a command outside the list needs a frame of its own while it runs; `binary format` reads no variable and runs no script, as `join` and `format` do.  (How much of the difference is the frame was not separated.)
* **What the check found: execution traces.**  The new differential cases (`pb_*`, `pe_*`) include `trace add execution` on `binary`, on `::tcl::binary::format`, on `string`, on `::tcl::string::first`, `::tcl::string::map`, `dict` and `::tcl::dict::size`, with the call made from compiled code through a compiled callee.  With the change as the fork made it, a trace on `binary` ran in the interpreter (6 events) and never in compiled code (0).  The same was already true of `string` at the commit before: a trace on `string` or on `::tcl::string::first` gave 0 events for `string first` (and the other string operations the executor does in place) reached through a compiled callee, against 6 in the interpreter.  The existing `pj_str` test had not found it, because it makes the call from the top level.  Cause: the interpreter dispatches `binary format` through the command `binary`, and a trace on it runs; compiled code calls the subcommand's C procedure (tbc_direct) or does the operation in place, and an execution trace changes no command epoch, so the guard (decision 19) did not see it.
* **The fix.**  (1) The guard's dependencies now include the `string` subcommands that the executor's own instructions stand for (`strfind`, `strrange`, `strtrim`, ...: `tbcStrOps`), so they are checked like a call by name; (2) the entry check looks at the execution-trace flag of every command it depends on and, for the ensembles `string`, `binary`, `list`, `dict`, `array`, of the ensemble command, which the runtime pins once (`tbc_ens_pin`) and an entry reaches through a one-byte mask (`TbcEntry.ens`); a call that finds a trace runs the interpreter's version, and nothing is withdrawn, so the next call after `trace remove` is compiled again; (3) a call of a pure subcommand from typed code hands over to boxed code at that instruction while its ensemble has a trace (a trace added while the proc runs), and `tbc_direct` also refuses.
* **A cost found and removed on the way.**  The first version made the ensembles dependencies of the guard of every entry.  `w05_json` compiled 1817.4M instructions before and 1888.1M with it (**+3.9%**), found by the 21-workload comparison; the dependencies are a lookup per name at every entry. * **What is not done.**  An execution trace added to a built-in while a compiled proc that uses it is already running is seen at that proc's next entry (typed code that calls a pure subcommand sees it at once, as above); the interpreter's own bytecode in flight does the same.  The ensemble pins are of the commands as they were when the first module loaded: an ensemble that is renamed away keeps its pin, which only makes entries use the interpreter's version more than needed.
* **Tests.**  `pb_pack`, `pb_loop`, `pb_chain`, `pb_all` (every format letter), `pb_lit`, `pb_catch` and `pb_err` over 20 values and 18 formats (errors included), traces (enter and leave) on the command and the ensemble, `rename` of `::tcl::binary::format` and of `binary`, an alias over `::tcl::binary::format`, `interp limit command`; `pe_*` for `string` and `dict`: 447 more calls in the differential test (17782 in all), four modes, forced hand-over, `TBC_FORCE_WPOLICY=1`.  The trace cases give a mismatch with the change of the fork and with the commit before it for the `string` cases.

## 38. Lazy attach goes through the proc's entry points, not an execution trace

A fork of this work reported that the default lazy attach (decision 3) turned the first call's arguments into a string, about 100M instructions for a 640 KB buffer, and advised attaching with `TBC_EAGER=1`.  That is a workaround, and eager attach has costs of its own (decision 3: 252M more instructions loading 20 tcllib packages, and more bytecode mismatches), so the cause is removed instead.

* **Measured.**  A proc that takes a 640 KB byte array, first call: interpreter 26 us; compiled, lazy attach **4788 us**; compiled, eager attach 15 us.  Cause: the attach waited for the first call with a one-shot execution trace on the proc, and Tcl gives a trace handler the whole command as text, so every argument was copied into a string (in plain Tcl a trace with an empty handler costs 8-10 ms on that call, nothing without it).  The argument also keeps the string form afterwards.
* **The change.**  An armed proc's command has entry points of ours in place of the interpreter's (`objProc` and `nreProc`; the client data, the Proc, is untouched, so `info body`, `info args` and `info procs`, which go by the delete procedure, see an ordinary proc).  The first call puts the interpreter's back, attaches (the interpreter compiles the body at that call, as before, so the bytecode compared is the one it runs) and makes the call as it would have.  Everything that tells a proc by its `objProc` accepts either (`TBC_IS_PROC_OBJPROC`).  A command whose entry points were taken by something else is attached at once.  The `::tbc::lazy` command and the trace are gone, so `trace info execution` shows nothing of ours for any proc.  First call, same proc: lazy **33 us**, eager 16 us.
* **Check.**  `tzb_lazy` in the differential test: a byte array passed to a proc at its first call must not have a string form afterwards, as in the interpreter; with the trace the compiled run gave `{1000 0}` against `{1000 1}`, now equal.  (My first version of this check reused the name `tz_lazy` of the report test and broke it: the full suite caught that; the names are separate now.)
* **Not done.**  Nothing found open; the eager attach cost of decision 3 is unchanged and still the reason for the lazy default.

## 39. Dict locals begun with `set d {}` are native maps with integer keys

## 48. Channel commands, `regexp` and `regsub` with result variables, and what each did on the real programs

The unsupported commands that typed code handed over at in tclbench's programs (`TBC_DEADOPS`) were channel commands (`gets`, `eof`, `tell`, `seek`, `read`, `open`, `fconfigure`, `close`) and `regexp` / `regsub` with result variables; each hand-over leaves a loop in boxed code unless typed code is entered again at a loop head (decision 47).
* **Channel commands.**  `eof`, `tell`, `seek`, `flush` and `read` are built-ins typed code calls through the pinned command (`tbc_direct`, decision 19), `gets chan` too (by its number of words: `tbcPureArity`); `gets chan var` is done inline for a local `var` (`getsVar`, `tbc_gets_var`: the channel is looked up and checked before anything is read, and the command makes the call when it is not found or not open for reading, so the errors are the command's; a read error afterwards is raised as the command does).  A loop `while {[gets $fh line] >= 0} {...}` over 100000 lines: **1.00x to 1.25x**.  `open`, `close`, `fconfigure` and `puts` remain boxed: they run once per file, not per line.  Like the other built-ins of that list these may run a script (a reflected channel's handler): one that reached into the calling proc's frame by `uplevel` would find locals that typed code holds unflushed, as it would for `puts` already (decision 21).
* **`regexp` and `regsub` with result variables** (`varWriteCall`, `varWriteArgs`): the locals that name result variables are stored to the frame, Tcl's own command is called, and the locals are read from the frame again.  Which words are variables is decided as the command reads its options, from the literal words (a non-literal word can only make the command read fewer variables than assumed, never others); a name that is no compiled local (`->` in `regexp $re $s -> a b`) is a variable the frame creates and typed code never holds.  A variable that is linked (`upvar`), an array or traced takes the boxed path (nothing has been done yet); the local is not stored or read when it is the frame's own object (the first version of this cost `w09_tokenizer` 1.4% for a store and a read at every call that boxed code, which keeps the variable in the frame, does not make; 1.1% remains, 1705M against 1682M instructions).  `rv_*`: 243 more calls.
* **Measured on the programs.**  `wordcount` 1.01x to 1.05x; `regexp`, `map` and `parse` stay at 1.0x because their time is in the regular expression engine and in other commands; `gccont` 1.32x.  On the workloads of decisions 19 and 28: `soundex` 1.21x to 1.39x, `csv` 1.01x to 1.06x, `textutil` 1.07x to 1.09x; `w09_tokenizer` 1.00x to 0.99x (regexp-bound, above).

## 49. A string built by `append` is a byte buffer; string equality and `string index` without calls

`bench/vs-c.sh` put `k_str` (a string built a character at a time by `append s [string index abc.. $i]`, then scanned with `string index $s $i` and `eq`) at 30x C and `k_lcs` (two such strings and a table of pair keys) at 33x; a profile of both showed the work in the generic string paths, not in the loops: `TclStringCmp` 92 instructions and `TclCheckEmptyString` 40 for each `eq`, `Tcl_GetCharLength` 36 and `tbc_s_index` 53 for each `string index`, `Tcl_AppendObjToObj` and `AppendUtfToUtfRep` 100 for each `append`.

## 50. A command replaced while a proc runs is seen as the interpreter sees it

A reflected channel's handler can run a script from `read`, `eof`, `tell`, `seek`, `flush` and `gets`, so those commands are not "pure" (decision 47 had listed them as such).  Looking at what such a script could observe in a compiled proc: **the caller's variables, no** (the handler is evaluated at global level, `uplevel #1` and `upvar #1` cannot reach the proc's frame, in Tcl and in compiled code alike: `cr_refl_vars`); **the commands it renamed or redefined, yes**.  That was a difference, and not only for channels: a proc that replaced `string`, `join`, `eof` or `tell` (itself, by a callee, or by a handler) was run by the interpreter with the new command from the next command on, and by compiled code with the old one, because the guard of decision 19 was made when the proc was entered.  It shows with plain procs (`cr_string`, `cr_join`, `cr_first`, `cr_typed`).
* **What the interpreter does.**  A proc whose code can run a script (`invokeStk`, `evalStk`, `upvar`, `yield`...) keeps `INST_START_CMD` at the start of its commands (the rest is compiled without: `IsCompactibleCompileEnv`).  After anything that could have re-entered the executor, that instruction compares the interpreter's compile epoch, and the epoch of the namespace's resolvers, with those the bytecode was compiled at, and a command that finds them different is **evaluated again from its source** (`instStartCmdFailed`: the command's text is compiled and run, its result takes the place of the command's, and the code goes on after it).  Every later command does the same, since the bytecode's epoch is never refreshed.  A name that is looked up at run time (`invokeStk`) is found as it is at that moment, through the command's own epoch.
* **What compiled code does now.**  Where the bytecode has the instruction, boxed code makes the comparison (after instructions that can have run a script, `epochChkG`: calls, evals, upvars and the access to a variable that lives in the frame, which can have a trace) and evaluates the command from its source, exactly as above: the source is compiled into the generated code, the result is pushed, the code goes on at the end of the command (a `break`, `continue`, error or `return` of that command goes through the proc's exception ranges as for any command).  Typed code makes the comparison after the instructions that can run a script (`epochChk`: not variable accesses, whose helpers hand over to boxed code for a variable with a trace), with a flag set by those instructions (the interpreter's `checkInterp`), and hands over to boxed code at the instruction when it differs.  The baselines of an activation (the two epochs, and the sum of the epochs of the namespaces and of the pinned built-ins of the module's guard, `tbc_gen_<module>`, which is what tells typed code that a built-in it calls through its pinned command, where the interpreter would look the name up again, is no longer the one that name stands for) are taken when the proc is entered (the sum when the first instruction that can run a script is about to run), carried through hand-overs and back into typed code at loop heads (`tbc_epb`, `tbc_nseb`, `tbc_genb`), and boxed code does not go back into typed code after a change.
* **Tests** (`cr_*`, 28 calls): `string` replaced by a callee in the middle of a loop, `join` and `lsearch` the same (pinned built-ins), a built-in replaced in a loop with typed variables and a string builder (`cr_typed`), a command defined in a namespace that shadows a built-in of it, `eof` replaced by a reflected channel's handler, the handler looking at the proc's variables with `uplevel` and `upvar`, a variable trace and an execution trace running `uplevel` on typed locals, `uplevel` changing locals, and a coroutine whose caller replaces `string` and `join` between resumes.  The differential test gives 6 mismatches without the change and none with it, and the forced hand-over runs (a hand-over at one typed instruction in 3 to 101) compare equal.  The first full-suite run of the change failed in fuzz typed seed 3 with forced hand-over: the break and continue targets of the instruction were not always instructions of the proc at that depth (fixed; the label is now only emitted when they are).
* **Cost, measured.**  The first version checked the baseline at every statement after a variable access, and made the 21 workloads up to 2.7x slower in instructions (`stats` +176%, `rc4` +167%, `crc32` +100%, `sha1` +55%) with equal results; the differential tests could not have shown it.  Typed code now tests a flag, and takes the module-wide sum only after a call; boxed code compares the epoch only.  Compiled instruction counts against the baseline of decision 47/48: `rc4` -25%, `soundex` -13%, `csv` -5%, `linalg` -3%, `binary` -3%, `blowfish` -2%, `stats` -1%, the others within +-1% except `yaml` **+4.8%** (ratio 0.97 to 0.92), `tokenizer` +2.5% and `sha1` +1.7%; the cause of those three has not been isolated, and `yaml` was already slower than the interpreter.  The decreases come from the string builder (decision 49), not from this change.
* **Not covered, and why.**  (1) A proc that yields (`hasYield`) had no such checks: its boxed code is entered again after each resume, where the baselines of its activation were not carried (`cr_ydrun` agreed with the interpreter, but the compiled code had not run in it: `cr_ydgen` calls `join`, which keeps a proc from running compiled in a coroutine).  Closed by decision 52, which found that it was a wrong result.  (2) The epoch of the namespace's resolvers is compared only in procs that have a frame (a proc called directly by typed code has none and, being pure, cannot run a script).  (3) A namespace created after the guard looked for it is seen at the next entry, not in the middle of a run.

Full-suite result: the whole of `tests/run.sh` from a snapshot of the commit before this entry (differential 18465 calls in four modes, forced hand-over, guard, typed, osr, hot, cmdmap, names, nest cap, capture, pristine Tcl, fuzz seeds, valgrind 18385 calls): exit 0, 0 mismatches.  The quick suite with `TBC_FORCE_WPOLICY=1`: 0 mismatches.  The 21 workloads: results equal.

## 52. A proc that yields sees a command replaced while its coroutine is suspended

Decision 50 left one case open: a proc that yields had no check that a command it uses was replaced, because its boxed code is entered again after each resume without the baselines of its activation, and it noted that `cr_ydrun` agreed with the interpreter.  The user decided to carry the baselines through the yield.  Looking at what `cr_ydrun` tested showed that it tested nothing: `cr_ydgen` calls `join`, so the proc ran the interpreter's version inside the coroutine (`coroutine_calls` +1 in `tbc::report`), and the agreement was the interpreter agreeing with itself.  A yielding proc that does run compiled (it uses only what keeps it yield-safe, and its coroutine is started from interpreted code: a `coroutine` command called by compiled code puts a C frame under it, which the proc then cannot suspend through) gave a **wrong result**: with `string` replaced while it was suspended the compiled coroutine returned `{4 4 4 4}` where the interpreter returns `{4 NEW NEW NEW}`.
* **Baselines.**  The epoch checks are made for procs that yield (`epochChkX` no longer returns none for them), the record of a yield holds the baselines of the activation (`ep_`, `nse_`), and the resume callback puts them back in `tbc_epb` and `tbc_nseb`, where the boxed code that goes on and the typed variant after the yield (`V_..._RE`, which also starts with a check pending, `rv_ = 1`) read them.  At the first command start after the resumption they are compared as in any proc, so the check is made as the interpreter makes it at the next command start of its stale bytecode.
* **A command evaluated from its source cannot be evaluated from the C frame.**  The interpreter goes on evaluating every later command from source, while its bytecode is stale, including the next `yield`; compiled code evaluated the source recursively (`TclNRRunCallbacks` in its own C frame), where a `yield` fails with `cannot yield: C stack busy`, which the first version of this change did.  For a proc that yields the command is now given to the interpreter's trampoline with the resume callback behind it (`tbc_do_eval`: the record is that of a yield, the callback pushes the result of the command and the boxed code goes on at the instruction after it, as after a yield; another result code, an error or a `return`, goes on at the command start's own error entry, `epc` of the record, which the yield uses too).
* **Tests** (`tests/report.tcl`, 16 scenarios: `cr_yd2`, `cr_yd5` to `cr_yd8` of `tests/procs.tcl`): `string` replaced by a command that returns, that fails with `error` and with `return -code error`, that calls the original, that breaks, that itself yields before it returns (evaluated by the interpreter's trampoline, as it must be); restored in the middle of the run (the epoch changes twice); a `catch` around the replaced command; the typed arithmetic after the resumption; a value yielded and received.  Each result is compared with a reference interpreter that has no module, and each run is required to have run compiled in the coroutine (the report's compiled calls up, calls handed to the interpreter not).  On the code before this change all 16 fail on the result (and none on having run compiled); with it none do.  The differential test (18574 calls) and the quick tests are unchanged.
* **Not changed.**  A proc that yields and was entered by compiled code runs the interpreter's version in a coroutine (decision 39).

Full-suite result: the whole of `tests/run.sh` from a snapshot of `8462f07` (`src`, `include`, `tests` and `tools` are the same in the commit of this entry): exit 0, 0 mismatches (differential 18574 calls in four modes, `tests/report.tcl` with the 16 yield scenarios in four modes, forced hand-over in six runs, guard, typed, osr, hot, cmdmap, names, nest cap in six runs, capture, pristine Tcl, lite, ubsan in four runs, fuzz typed seeds 1 to 3 and boxed 1 and 2, valgrind 18488 calls). ## 53. A matcher of our own for the regular expressions of a subset, with a state cache that lives as long as the program

What the profile said: `miss` and `getVacantSS`, Tcl's construction of the states of its matcher, were 17% to 25% of the instructions of `json`, `tokenizer` and `textutil`.  Tcl builds them again for every execution of an expression and cannot keep them without changes to Tcl, which are not made.  `include/tbc_re.h` is a matcher that keeps them: a Thompson NFA of the expression, and a DFA made state by state as the input needs it and kept (at most 300 states and 3000 NFA nodes an expression; more, and the expression is left to Tcl).
* **Exact by construction, as far as it can be.**  The text of the pattern is parsed only as far as its structure goes (alternation, non-capturing groups, the greedy quantifiers `* + ? {m} {m,} {m,n}`, an anchor at each end of the whole expression).  What each single-character atom matches (a literal, an escape, `.`, a bracket expression, `\d \s \w` and their negations) was first asked of Tcl's own matcher, a character at a time; it is now worked out here for the common forms (`tbc_re_atomown`: literals, escapes, ranges, the classes, `[:alpha:] [:digit:] [:alnum:] [:upper:] [:lower:] [:space:] [:xdigit:] [:blank:]`, `^`), because each distinct atom cost 137 executions of Tcl's matcher, 0.2M to 0.3M instructions, which a program that uses its patterns a few times does not get back (`base32` fell to 0.97 with it).  **That part is checked, not constructed:** with `TBC_RE_VERIFY` set (the fuzz test sets it) every atom is also asked of Tcl's matcher (a scan of one string of the probe characters, or one execution a character), and the matcher aborts on a difference.  The fuzz found two errors of the first version of the own parser at once (a negation with the wrong value, and `[\D]`, which Tcl 8.6 reads as something other than the complement of `[\d]`, so it is left to Tcl).  Any atom that is not of these forms is asked of Tcl as before.
* **Characters above U+007F.**  An expression whose atoms treat them alike (a plain bracket expression, a negation, `.`) sees them as one symbol.  One with a class of Unicode (`\d \s \w`, `[:alpha:]` ...) asks Tcl's matcher about each distinct character of the subject above U+007F, once, and gives the characters its classes treat alike a symbol of their own (at most 8; more, and the call is left to Tcl).  Nothing of Tcl's tables is copied.  A first version took such expressions on subjects of ASCII only, and `json`'s document holds one `é`, so its tokenizing call was passed to Tcl every time (json 1.00); the cause was found with the profile (`Tcl_RegexpObjCmd` called 300 times from the interpreter, then from `tbc_evre`).

## 54. An expansion inside an expansion, in a loop: the handler of the inner one sees the outer marker

Found by running tcl-aot over the TclQuest engine (three of its 220 procs were refused with "inconsistent stack depth"): `foreach s $l { lappend r {*}[string cat {*}$s] }` is valid Tcl and runs in the interpreter, and tcl-aot refused it.  `g1` to `g8` in `tests/procs.tcl` (`sd_*`) are the shapes; `for`, `while`, `append`, `set`, a global and a nest of two commands all failed the same way.
* **Cause.**  A command that ends with break or continue sends the interpreter to the handler of the innermost exception range around it.  For the inner `invokeExpanded` the compiler makes a range of its own (`level 1, loop, pc 38-38`) with a handler `expandDrop; jump <the loop's break>`.  The translator gave that handler the expansion markers that were open at the range's first instruction, which include the inner expansion.  [read in source: `tclExecute.c`, `INST_EXPAND_DROP` and `processExceptionReturn`] `INST_INVOKE_EXPANDED` has already taken its own marker off the auxiliary stack by then, so the `expandDrop` of the handler drops down to the **outer** marker.  With the wrong marker the handler's depth was two too high and its jump to the loop's target disagreed with the loop's own flow.
* **Fix.**  The markers at the target of an edge that leaves an `invokeExpanded` are those of the instruction minus its own (one line in `prepare`).  Nothing else changed: the depths of every other proc are the same, and the handler is now walked with the depth the interpreter has.
* **Tests.**  `sd_cat`, `sd_for`, `sd_while`, `sd_append`, `sd_nest`, `sd_global`, and the ones whose inner command ends with `break`, `continue`, `error` or `return` (`sd_break`, `sd_while_break`, `sd_for_break`, `sd_catch`, `sd_two_loops`: the interpreter runs the loop's break and continue correctly, so a first idea, to drop the edge, would have been wrong and is not used): all compiled (`mustAttach`), 0 mismatches in the differential test (results, return codes, error info), plain and with forced hand-over.  Before the change the translator refuses all of the first group.

## 55. `max()` and `min()` in expressions are typed, and the other math functions take tagged numbers

Measured on the TclQuest engine (about 140 uses of `max` and `min`): 1,000,000 iterations of `set s [expr {$s + max($i % 7, $i % 5, 2)}]` took 429 ms compiled, against 1.7 ms for the same test written `?:` (250x); interpreted 383 ms against 76 ms [measured, `repro/r5.tcl` of the engine study].  `max` and `min` are not commands in C but procs of Tcl's library (`init.tcl`, TIP 255) that take `args`, so a call was a call of a proc through the interpreter, and a proc that used them was not pure, so none of its compiled callers could call it directly either.
* **Semantics reproduced.**  The library proc starts `val` at `-Inf` (`Inf`), converts every argument with `double($arg)` (which raises the interpreter's own error for text) and takes each one that is strictly greater (less) than `val`: the **first of equal values wins and the result is the argument itself**, not a number made from it (`max(0x10, 3)` is `0x10`, `max(2, 2.0)` is `2`, `max(-0.0, 0.0)` is `-0.0`).  Typed code does the same (`mmFunc` in `translate.tcl`): all operands integers give an integer, all doubles a double, integers and doubles together a tagged number (W) in a proc that uses W and otherwise the object; an object operand is read with `tbc_num` and the result is that object (or the literal's object when a literal wins: a literal written `0x10`, `1e3` or `2.50` comes back as written, which is checked at translation time).  Integers and doubles compare as Tcl compares them (exactly; with the same 2^53 limit and hand-over as the arithmetic comparison).  Text, a bignum, an operand count of 0 or more than 8, anything else: hand-over before anything is changed, and the library proc reports it.
* **When it is valid.**  Only while `::tcl::mathfunc::max` and `min` are the stock procs: the translator compares the hash (FNV-1a) of their bodies with the ones of Tcl 8.6.14, and so does `tbc_mf_setup` when the module loads; it also puts a rename and delete trace on them and the existing flag `tbc_mf_ok` (cleared when a proc named `...::tcl::mathfunc::...` is defined, when one is renamed or deleted, when another namespace has a `tcl::mathfunc` with commands in it) guards each call.  `mm_redef` renames the stock `max`, defines another, calls compiled procs that use `max`, restores it: results equal to the interpreter's.  A program that defines its own `max` (or runs in a safe interpreter, where it is an alias) gets the ordinary calls.
* **Pure again.**  A call of the stock `max` or `min` is not a call of a proc to the analysis any more: a proc that uses only them (and arithmetic) is pure, and its callers call it directly (`mm_helper`, `mm_call`: `returns I`, typed direct call).
* **The other math functions** (`abs sqrt hypot floor ceil fmod int double round sin cos atan2 acos asin exp pow`, and `**`): checked one by one with all operand kinds (I, D, B and in W procs), they were already typed for I, D and B; `abs`, `int`, `wide` and `round` of a tagged number (W) handed over to a call of the command and are now typed (`mw_funcs`, `mw_one`).  Not typed: `isqrt`, `bool`, `entier`, `abs` and `round` of an object in a proc without W (they go through the generic call; not measured to matter).
* **Tests.**  `mm_*` and `mw_*` in `tests/procs.tcl`, 25,976 calls in the differential test in all, 0 mismatches: every pair of 28 values (integers at the 2^53 and 2^63 edges, a bignum, `0x10`, `010`, `" 5"`, `1e3`, `1.50`, `-0.0`, `Inf`, `abc`, an empty string, `true`), one to eight arguments, ties in both orders, a loop that keeps the result of the previous round, a clamp `max($lo, min($hi, $x))`, a call through a namespace.  `tests/typed.sh`: no hand-over at the call of `max`/`min` (it fails with the translator before this change) and the kinds of the results.
* **Measured** (`repro/r5.tcl`, 1,000,000 iterations, ms): `max` of three integers 383 interpreted, 429 compiled before, **0.9** after (the `?:` form 0.9); of doubles 305 interpreted, **0.6** after.

## 56. `lassign` throws away the rest of the list it does not use, and `lindex` with several indices takes the elements one at a time

Found on the engine (the records of its sector pass are lists of 176 numbers, and `lassign $rec ax ay bx by` reads four of them): the proc ran as fast compiled as interpreted (42 us against 43 us a call), and with four `lindex` instead it ran in 12 us.  Two causes, both general.
* **`lassign` builds a list it does not use.**  `lassign $rec a b c d` is compiled as `dup; listIndexImm 0; storeScalar; pop` for each variable and then `listRangeImm 4 end; pop`: the rest of the list, 172 elements here, is copied and thrown away in every call.  [read in source: the bytecode of `lassign`; measured with `tcl::unsupported::disassemble`]  Typed code (and boxed code) now look at what the next instruction does with the result: when it is a `pop` that nothing else reaches (`deadResult`: not a jump target, not the exit of a loop or catch range), the copy is not made and only `Tcl_ListObjLength(NULL, ...)` checks that the value is a list, because `lrange` fails exactly when it is not one; the slot keeps the list and the `pop` releases it.  When the check fails the boxed code runs the real `lrange` and reports its error (after the `listIndexImm` before it would have failed first anyway).  When the value of `lassign` is used (`set rest [lassign $l a b]`, `[llength [lassign ...]]`) the instruction is as it was.  This is a rule about the instruction, not about `lassign`: any `lrange $l 4 end` used as a statement benefits, with the same result.
* **`lindex $m $i $j` and `lindex $m {1 2}` were calls of the command with boxed operands** (`lindexMulti`, and `listIndex` with a literal list as index): 31 ns an element against 2.7 ns for `lindex [lindex $m $i] $j`, which has an instruction of its own, and interpreted the multi-index form is 2x slower than the nested one, too (482 us against 232 us for 10,000 elements).  With integer indices (typed integers, objects that are integers, or a literal list of canonical integers, up to eight) `lindexChain` takes the elements one at a time with `tbc_lindex_i`, which is what the nested form does, so the result is the same: an index out of range gives the empty string and the next level of the list is then the empty string, a value that is not a list or an index that is not an integer (`end`, `1+1`, text) hands over before anything has changed and the command reports it.
* **Tests.**  `la_*` (14 shapes: the value used, fewer and more elements than variables, a placeholder, a shared list modified afterwards, an invalid list, a list of 176 numbers, a loop, a nearest-wall search over records) and `lx_*` (multi, three levels, constants, `end`, a loop of integers and of doubles, 16 values of the index, 9 lists) in `tests/procs.tcl`: 26,935 calls in the differential test in all, 0 mismatches.  `tests/typed.sh` checks the structure: the typed code of the lassign procs has no `::lrange` where the result is thrown away (and has one where it is used), and no call of `::lindex` for the multi-index forms (both fail with the translator before this change).
* **Measured** (compiled / interpreted, us a call, `bench` procs of this change): nearest wall over 146 records of 176 numbers with `lassign` 25.7 interpreted, **15.4** compiled (before the change the same as interpreted), with four `lindex` 22.7 and 15.6; `lindex $m $i $j` over 100 x 100 integers 489 interpreted, 314 before, **25.8** after; the same with doubles added 553, 305, **26.7**; `lindex $m {1 2}` and `lindex $m 1 2` 8.9, 6.4, **0.8**.
* **Not done.**  What is left of the 15 us of the lassign loop (146 records, about 100 ns a record against about 1 ns in C) is in the list elements being objects that are read as numbers at each use, not in the copy; see the engine measurements.

## 57. Procs that only read namespace variables are called directly, with no frame

The first blocker of the engine study: a call from compiled code to a proc that reads a namespace variable was a full interpreter call.  Pure callee (arguments only): 123 ms to 0.8 ms for 1,000,000 calls (150x).  Callee that reads one `variable`: 154 ms to 174 ms (0.9x), and the same with `$::ns::K` [measured, `repro/r6.tcl` of the engine study, rebuilt here as `nv` in the bench].  Every helper of the engine's sector pass (`irradianceLin`, `vis`, `occ3`, `trace`, `wallDist`) reads `variable ON`, `REC`, `F(...)`, so the whole chain was `invokeStk1` at every level.  Roadmap item 4 asked for this.
* **What is called without a frame.**  A proc is a *reader* when it is pure except for (1) links made by name with literal names: `variable name`, `upvar #0 target name`, `global name` and `namespace upvar ::ns target name`; (2) reads of the variables so linked (`loadScalar`, `loadArray`: `$K`, `$F(a)`); (3) reads of a literal absolute name, `$::ns::K` and `$::ns::F(a)`.  Every variable it has in its frame must be one of those links, never written, never used any other way (`info exists`, `incr`, `append`, `unset`, `foreach` variables, the arguments of a command all take it out of the class).  Callers treat it as pure: a direct C call of its typed variant with `inframe` 0, guarded by the same flag as any direct call (cleared when the callee is renamed, deleted or redefined), the result in the C return value.
* **The frame it does not have.**  The typed code of a reader works on a private array of locals (`floc_`, only the entries of the linked variables, zeroed at entry); a link is a link variable in it, to the namespace variable, which is what `variable` leaves in a real frame, so every helper that follows links (`tbc_tld`, `tbc_tald`...) is used as it is.  No instruction of the interpreter's frame is involved.  When the proc is entered from the interpreter (inframe 1: a call from a script, a loop head) it runs in its real frame as before, with the real `variable` instruction.
* **Finding the variable (the part to check).**  A lookup by name costs about what the interpreter's `variable` does (the 160 ns of the call), so the result is kept per call site (`TbcNvSite`) and each use costs a few comparisons.  The variable found is the `Var` the interpreter would find *and the site holds a reference on it* (`VarHashRefCount`): while it is held `unset` leaves the entry (undefined), and a later `set` finds the same `Var`; when its namespace is deleted Tcl marks it `VAR_DEAD_HASH` and takes it out of the table, which every use looks at, and the next use looks the name up again, finds the new namespace's variable and holds that one (`nv_reset 5.5 70` etc. in the differential test: a namespace deleted and made again with other values, three times, each read compared).  An interpreter-wide resolver, or a resolver of the global namespace or of the variable's namespace, turns the fast path off.  A different interpreter, or the same address after an interpreter was deleted (`tbc_nv_epoch`, bumped by `Tcl_CallWhenDeleted`), starts again.  Names are read from literals only, absolute (`::ns::K`) for the reads, relative to the proc's own namespace for `variable`.
* **Everything unusual is the interpreter's.**  The variable is missing, unset (`unset`), an array where a scalar is read or the other way, has a read trace, a link to something of that kind: `tbc_tld` and the others say no (as they do for a frame variable), the typed code hands over, and since a reader has changed nothing and runs no script, the whole call is made the ordinary way (`tbc_st` 3: boxed arguments, `Tcl_EvalObjv`), which creates the variable for `variable` as the interpreter does, runs the trace, raises "can't read ...: no such variable" with its own error info.  `nv_*` in the differential test change `K` to an integer, a double, text, `0x10`, unset it and set it again, make it an array, trace it (read trace on a scalar, on an array and unset trace), delete and recreate its namespace, rename and redefine the callee between compiled calls: all compared, results, error codes and error info.
* **`$::ns::K` in any proc.**  The typed code of `loadStk` and `loadArrayStk` for a literal absolute name (before: an instruction typed code had no code for: it handed over, boxed code did the read, and typed code resumed at the next loop head) uses the same kept variable: it is typed in every proc, not only in readers.
* **Not done, and why.**  Writes: a proc that sets or increments a namespace variable (a counter, a cache) has effects before any later hand-over could happen, so it cannot simply be called again the ordinary way; it needs a frame that can be built on demand at the hand-over (roadmap item 4 in full) or a rule for which writes can be made first.  Relative qualified names (`$ns::K`), `info exists` on a linked variable, `uplevel`/`upvar` to other levels: these stay calls through the interpreter.  A reader that reads a double where the proc has no sign of floating-point numbers (no double literal, no `double()`) hands over at every call, because typed code assumes integers (decisions 29 and 30: the adaptive version exists for procs with a loop that accumulate, not for a loop-free helper): the engine's helpers all have double literals, but `proc scaled {x} {variable K; expr {$x * $K}}` with a double `K` is still an ordinary call every time.
* **Tests.**  `nv_*` (11 readers: `variable` with a qualified and an unqualified name, in a namespace and out of one, `upvar #0`, `global`, `$::ns::K`, array elements read by `variable`, by `$::ns::F(a)` with literal and computed keys, a string variable, a reader that calls a reader, one with `max`) with about 140 calls in the differential test; `tests/nv.sh` (a module built with `-DTBC_COV`: 1000 calls of three readers from a compiled loop enter their typed code 1000 times and never hand over; with a read trace on `K` the same calls run the trace (9 times for 3 rounds) and give the same result; it fails with the translator before this change).
* **Measured** (`bench/nv`, 1,000,000 calls of a loop-free helper, ms; interpreter / compiled before / compiled now): pure helper 110 / 0.8 / 0.8; `variable ::ns::K` 163 / 174 / **10.1**; `$::ns::K` 158 / 171 / **9.9**.  What is left of the 10 ns is the link (cache lookup and two stores), the read through it, and the object K read as a number (C: about 1 ns).

## 58. A variant that takes a double uses tagged numbers for the objects it reads

Found with `tbc::hot` on the engine after decision 57: `zAt` (`variable PL; set b ...; expr {[lindex $PL $b] + [lindex $PL $b+1] * $x + [lindex $PL $b+2] * $y}`, a loop-free helper that the sector pass calls 176,528 times a frame) handed over at its multiplication in **every** call (100% of its entries), so each call ran again through the interpreter and took the direct-call chain above it (`ceil0`, `stepAt`, `wallDist`) with it.  Cause: typed code takes an object operand of an arithmetic instruction to be an integer unless the proc "has a sign of floating-point numbers" (a double literal or a call of `double`, `sqrt`...: decision 29), and `zAt` has none: its doubles arrive as arguments (`x`, `y` are `D` in the variant the callers reach) and as list elements.  The adaptive version of decision 30 needs a loop to re-enter.
* **Change.**  A variant whose signature has a `D` has the sign: `wpolK` (the policy of one variant) is true when the signature of the variant holds a double, like a proc with a double literal.  Objects it reads are then tagged numbers (W), and the variants without a double argument are as before.  It is the variant, not the proc: `zAt/IIII` stays integer code.
* **Measured.**  `zAt` handed over 176,528 times in 176,528 entries of a cove frame; now 75 times (the first frame's cache warm-up and the values that are not numbers).  `tests/nv.sh`: a helper `nv_at {pl b x y}` called 1000 times from a compiled loop with doubles enters its typed code 999 times and never hands over (it hands over in every call with the translator before this change) and gives the interpreter's result.  The differential test (27,065 calls) and the rest of the suite are unchanged: W code is the code the forced-policy runs have always tested.
* **Not changed, and what is next.**  A value read from a list that is a double *with a string form* (a list built from text, or printed once) cannot be held unboxed as a variable's value, because boxing it again would give another text (decision 29's rule: accepted only in canonical forms): a store of such an element into a variable that is used as a number hands over (`ceilT` of the engine: 34% of its calls hand over at one such store). ## 60. One step from a program to its compiled self: `tools/tcl-aot build`

The designer's aim (K63): any existing Tcl or Tk program plugs in unchanged and runs as fast as possible.  Until now a user listed the procs, translated, built a module, linked a shell, and procs made at run time were missed unless the program called `tbc::capture` (decision 8's loop, by hand).
* **The step.**  `tools/tcl-aot build -o out [-also 'ARGS']... PROGRAM ARGS` (POSIX sh, decision 59): (1) builds a shell with the runtime and no code (`tools/module-shell.c` with a one-proc module); (2) runs `PROGRAM ARGS` in it with `TBC_CAPTURE=file` (the capture of `tbc::capture`, on from the first command, written by an exit handler with stdio because the interpreter may be gone when it runs), once per `-also`; (3) merges the files (`tools/tcl-aot-merge.tcl`: each definition once, in the order first seen); (4) translates; (5) builds the module (`tools/build-module.sh`, `-split` defaults to the number of processors above 100 procs); (6) links `out/shell`.  `out/shell PROGRAM ARGS` runs the program with the module started before its first command (`-DTBC_AUTOLOAD`); `TBC_OFF=1` leaves the module out, which makes the same executable the interpreter alone, the reference for a comparison.  No change to the program: no list of procs, no `load`, no `tbc::capture`.
* **Why record a run and not read the source.**  A proc's definition is what the interpreter has after the program ran: `string map` and `regsub` builds, `source`d files, `eval`, packages.  The recorded text is exactly the namespace, arguments and body the module's key needs (decision 8).  A proc no run defined stays interpreted with the interpreter's results (the key does not match): a run that misses code paths costs speed there, never correctness; `-also` adds paths.  `-after MS` ends a recording run of a program with a window after that long in the event loop.
* **Shells.**  A tclsh (`Tcl_Main`) is the default; with a static Tk built (`make tk`) `package require Tk` finds it (`Tcl_StaticPackage` and the `package ifneeded Tk <version> {load {} Tk}` that a `pkgIndex.tcl` gives a shared Tk, which a static one lacks: found when `package require Tk` failed).  `-wish` makes it a `wish` (`Tk_Main`, Tk_Init at start).  The module is started after `Tk_Init` in a wish and, in a tclsh, before `package require Tk`, so the procs of Tk's own library are recorded and compiled in the second case (357 procs of a one-label program, 5 s to build).  The directories of Tcl's and Tk's library scripts are compiled in (`TBC_TCL_LIBRARY`, `TBC_TK_LIBRARY`; the environment wins).
* **Static Tk** (`make tk`, `tools/env.sh` for the flags): Tk 8.6.14 (sha256 8ffdb720...1a94, computed on the download; it agrees with the value I remember the Tcl site publishing, which I have not checked against the site) built out of tree, `macosx/configure --enable-aqua` on macOS (the one place the platforms differ, in the Makefile and `tools/env.sh`), `unix/configure` elsewhere (X11 development files needed: [not tested]).  **Tcl and Tk are now configured with `CC="$(CC)"`** (default `cc`): the Tcl of `build/` had been built by the first `gcc` in PATH, which on this Mac is a GNAT GCC 15 prerelease without the CoreFoundation headers, and Tk's Aqua code needs a Tcl built with CoreFoundation (configure said "Aqua can only be used when CoreFoundation is available").
* **The engine, through it** [measured, macOS arm64, Tcl and Tk 8.6.14 static, `TQ_NATIVE=0 TQ_SOUND=0`, the live checkout of `games/tclquest` read only, nothing written into it]: `tools/tcl-aot build -also "-slice .../sectors_cove.tcl -win 192x108 -frames 1 -shot x.png" main.tcl -slice tests/scenes/sectors_test.tcl -win 192x108 -frames 1 -shot y.png`: 961 definitions (899 procs: all translated), 2116 variants, no hints; 456 MB of C, a 142 MB object, a 10 MB shell; recording 293 s (both scenes in the interpreter, the machine busy with the test suite), translation 910 s, C compiler 1310 s (4 at a time) [the machine was loaded]. `main.tcl -slice ... -frames 1 -shot` through `out/shell` and through `TBC_OFF=1 out/shell`: the PNGs are byte-identical (sha256 e09f0dea... for sectors_test, a419542b... for sectors_cove), and have the same pixels as `wish8.6` 8.6.18 gives for sectors_test.  Whole-process time at 192x108: sectors_test 8.50 s interpreted, 5.77 s compiled; sectors_cove 269.75 s, 90.12 s.  The harness of `docs/research/tcl-aot-engine` at 96x56, best of N, ms (crc32 of the buffers equal in every scene): see PHASE-A2.md.  `tqnative.dylib` of the game's `lib/` loads into the static shell (`package require tqnative` gives 1.0), and the C twins built with critcl against the system's Tcl run in it: the C twin times of PHASE-A are reproduced.
* **Hints are not needed.**  The module of PHASE-A had the engine's hand-written `-hints` (36 lines); this one has none and is within 5% of it on every scene (cove 2737 ms against 2587, vault 1686 against 1634).  A recorded signature profile as automatic hints is not worth building on this evidence.
* **Limits** [read in source, not all tested].  A proc defined twice under one name with different bodies keeps the last in the translator (the earlier one stays interpreted).  The module is for Tcl 8.6.14: the program runs on the shell's 8.6.14 and Tk 8.6.14, not on the system's.  The library scripts are found by path; embedding them in the executable is not done.  A live window and event loop through the shell (as opposed to `-frames N -shot`) was not run: there was no window server when I tried after the build [measured: `wish8.6` of the system printed nothing and its `package require Tk` hung at that time].
* **Tests.**  `tests/dropin.sh` (in `tests/run.sh`): a program with a sourced file, a namespace with a variable, procs built at run time and one defined only for other arguments, with `exit 3` in the program; the output and exit status of `out/shell` equal the interpreter's for four argument sets, the procs of all recording runs are attached; and, when a static Tk is built and a window system is there, a Tk program.

## 61. A double that has a string form is held unboxed when its text is the one Tcl prints

Gap 1(b) of the engine study: `ceilT` handed over at the store of `dr` in 34% of its calls (70,445 of 202,372 per cove frame) because the value, a list element, was a double with a string form (a number read from the scene text and parsed once), and typed code held a double only when the object had no string form: boxing it again would give another text.  The same test (`tbc_arg_dbl`) decides which typed variant an interpreted call enters, so a variant with `D` arguments was refused for the same objects and the call ran the generic one.
* **Rule.**  A double object with a string form is accepted when that string is exactly what Tcl prints for the value (`Tcl_PrintDouble`): boxing it again yields an object whose text, made when someone asks for it, is the same string; any other text (`2.50`, `1e3`, `.5`, `0.10`, `1_0`, `inf`) is refused as before.  Nothing else changes: integers already needed their canonical text, and a string that was never parsed as a double is not a double object.
* **Cost.**  Whether a text is canonical depends only on the text (and the value that goes with it), so the answer is cached by the text in a table per thread (`tbc_cc`, 512 slots, the whole text and the bits of the value compared, no hash collision can give a wrong answer): a hit costs a hash of at most 29 characters and a comparison; a miss one `Tcl_PrintDouble`.  The function is `noinline`: inlined into the thousands of sites, the first try made the C compiler take over 20 minutes more on the engine.
* **tcl_precision.**  How Tcl prints a double depends on `tcl_precision`.  The module puts a write and unset trace on that variable at load; once it fires, texts are not accepted any more for the life of the process (`tbc_cc_off`).  The one exposure that remains is a typed frame that holds an accepted value while a callee changes `tcl_precision` and the frame then boxes the value: the new text can then differ from the old.  `trace info variable tcl_precision` shows the module's trace (the module already traces commands it pins).
* **Tests.**  `cd_*` in `tests/procs.tcl`, 126 calls in the differential test (21 lists: canonical texts, `2.50`, `1e3`, `.5`, `+1.5`, `Inf`, `inf`, `0x10`, `1_0`, `-0.0`, 17-digit values, a bad element, an empty list; as arguments entered unboxed, as stored and kept elements, and with `tcl_precision` set to 3, 17 and 0 inside the procs, the calls that write it last because they switch the acceptance off): 0 mismatches; with the acceptance forced on for every text the test fails (checked).  `tests/dbltext.sh` counts the entries: `cd_helper` takes its `DD` entry for the canonical texts (8 times) and the generic one for the others (63).
* **Measured.**  The engine's cove frame with a module built with the engine's hints (`tbc::hot`, 96x56): `ceilT` hands over at `dr` 2 times in 202,372 calls (was 70,445), `wallDist` takes its `IDDDI` entry 232,340 times and never hands over.  The frame time did not change (2,665 ms against 2,587 in PHASE-A, 2,737 without hints): the hand-overs were no longer where the time is.  The samples of the compiled cove frame are in the typed loop of `wallDist` itself and in object allocation and release (gaps 2 and 3).

## 62. The translator took time quadratic in the size of the program: `array names VK pattern` for every variant

## 63. Tagged numbers that are assigned on some paths only are held unboxed in procs that are not pure

Found in the engine study (PHASE-A3 of the notes): the hot typed variant of `wallDist` (`foreach` over 146 records, a few of which reach floating-point code that assigns `px`, `py`, `ux`, `uy`...) boxed every one of its tagged-number locals (`W`: integer or double, decided at run time) into a new `Tcl_Obj` at each store and freed it at the next, and the samples put the object allocator and `TclFreeObj` at about half of its time.  Cause [read in source]: a proc that is not pure (it can be asked about its variables by name: here a rarely taken branch calls `stepAt`, which reaches a proc that writes a variable, so the whole call chain is not pure) must write the variables that were assigned on the way taken into its frame when it hands over, and no others; a variable assigned on some paths only is held unboxed *with a flag* `g<v>`, but only for kinds `I` and `D`: `W` (and `A`, `M`, `Z`) were turned into objects (`flaggedOf` in `analyze`).  So the double-valued locals of a polymorphic variant were objects whenever any callee in a branch was impure.
* **Change.**  `W` joins `I` and `D` as a flagged kind: the flag is set by every store into the variable (the tagged store, the loop variable of a `foreach` over a vector, the loader that re-enters typed code from the boxed code, a `specStore`), the boxing code that runs when typed code hands over writes the object only if the flag is set, the re-entry loader sets the flag from the frame (variable present or not).  Variables that may be read before they are assigned are still objects (as before).  No change to the emitted code of procs without such variables.
* **Tests.**  `fw_*` in `tests/procs.tcl` (and `differential.tcl`): non-pure procs with numbers assigned on some paths only, with integers, doubles, strings, non-canonical texts, a list element, a trace on one of the variables, hand-overs in the middle of the loop (a call to an impure proc, errors), and a read of every variable by name at the end (`info locals` and `uplevel 0`: the compiler does not count that as a use), so a variable that was never assigned must stay unset and one that was must come back with the interpreter's value.  The differential test (27,401 calls, four modes) has 0 mismatches; with the flag test removed in the boxing code the test fails (checked).
* **Measured.**  `wallDist` of the engine on synthetic records (146 records of 190 numbers, 12 sectors; ns per record, compiled, one impure callee in a branch): 22.5 before, 14.4 after (13.4 when the callee is pure, which is what the unboxed version cannot beat without the later items).

## 64. `binary scan` and `scan` with variables are called from typed code like `regexp`: the proc stays typed

`::tq::surf::texel` of the engine handed over at every entry (6,583 of 6,583 per cove frame, `tbc::hot`: "unsupported" at `invokeStk1 ::tcl::binary::scan`): its `binary scan $data @[expr {...}]cucucucucucu r g b nx ny nz` has a format built at run time and six result variables, a shape the inline `binary scan` of decision 35 (literal format, one variable) does not take, so the whole call continued in boxed code from there. Found with `tbc::hot` on the engine (`plane` hands over at `storeStk` in 77% of its entries, `wallCol` at `storeStk` in 202 entries a frame): decision 57 typed the *read* of a variable by literal absolute name (`$::ns::x`: the variable is found once, kept, and anything unusual hands over), but the store (`set ::ns::x v`, instruction `storeStk`) and `incr ::ns::x` (`incrStk`, `incrStkImm`) had no typed code, so a proc that sets a namespace variable even once left typed mode there and ran the rest of the call as boxed code.

## 67. Elements of namespace arrays by their literal absolute name: store, increment and `info exists` are typed

## 68. The rest of a `lassign` is not built when the statement is an `if` or `switch` branch (the value is thrown away at the merge)

Found by sampling the engine's `sectors_test` scene (PHASE-A4 of the engine notes): 75% of the compiled frame was `Tcl_NewListObj`, `FreeListInternalRep` and the object release, all from `::tq::seg::trace`, whose per-record statement is `if {$COLM} { lassign [colEnds $rc] ax ay bx by } else { lassign $rc ax ay bx by }` with records of 176 numbers.  Decision 56 stopped `lassign` from copying the rest of the list (`listRangeImm 4 end`, 172 elements) when the next instruction is a `pop`, but a branch of an `if` does not end in a `pop`: the last command of a branch leaves its value on the stack, a `jump` takes it to the merge point and the `pop` of the `if` statement is there (and is also reached from the other branch).  `deadResult` said "not dead" for both branches (the `pop` is a jump target), so every record built and freed a list of 172 elements.
* **Change.**  `deadResult` also follows the way from the instruction to a `pop`: it may pass `nop`, `startCommand` and `jump1`/`jump4` only; any other instruction (a store into a variable, which keeps the value on the stack, a `dup`, a `done`) ends the walk with "no", so `set r [lassign $l a]`, `if {...} {lassign ...}` as the last statement of a proc and `set x [if ... lassign ...]` still build the list.  The pop releases the slot, which holds the original list, as decision 56 arranged; a pop that other paths reach with their own values (an `if` without `else` pushes the empty string, another branch another command's result) is as it was.  Typed and boxed code share the function.
* **Tests.**  `ld_*` in `tests/procs.tcl` (15 procs; `differential.tcl`, 247 calls: the value used or not, `if` without `else`, nested, `switch`, loops with `break` and `continue`, `catch`, a shared list that is modified afterwards, short, long and invalid lists): 27,969 calls, 0 mismatches in the four modes; `tests/typed.sh` checks that the typed code of `ta_branch` has no `lrange` (it has two with the code before this change) and that `set r [lassign ...]` still has one.

## 69. The value that an `if` statement leaves for its `pop` is never boxed; a number stored into a variable that holds an unshared number is written into that object

Found with `sample` and `atos` on the engine's `wallDist` (PHASE-A4): about a third of its time was one release call at a `pop` right after `storeScalar` of a tagged number into an object variable.  Two separate costs, both general.
* **The dead value.**  The last command of a branch of an `if` leaves its value on the stack; the other branch (or the missing `else`) leaves another kind (`set sp $q` gives a tagged number, `else` an empty literal), so the join of the two stack states was an object, and the branch that had a number boxed it (`tbc_newdbl`) and the `pop` at the merge released it at once.  `deadTop` already turned the value of the vector kinds (A, M, Z) into "no value" (X) when the target instruction is a `pop`; it now does so for integers, doubles, tagged numbers, literals and objects too.  An object is released on the edge into the pop (`edgec`); nothing else changes.  A proc that yields keeps the old states (the value a `yield` leaves is what a resume gives back to typed code).
* **A number into an object variable.**  `set sp $q` where `sp` is held as an object (it is a number on some paths and text or a literal on others) allocated a new double object and released the old one at every store.  `tbc_st_dbl` and `tbc_st_int` write the new value into the object the variable holds when the variable is its only reference (`refCount == 1`), it is a number of the same kind and it has no string form: nothing can see the object (any other holder would have made `refCount` 2: the small-integer table, literals, a list, a variable that was copied from it), so the result is what a new object would give.  Any other case allocates as before.  Counted in the engine's `wallDist` micro-benchmark: 681,165 stores wrote into the object, 574,394 allocated (497,894 because the object was shared).
* **Tests.**  `dt_*` in `tests/procs.tcl` (9 procs, 246 calls in `differential.tcl`: numbers, text, lists, literals including `0x10`, `switch`, `elseif` chains, nested, `catch`, a loop that leaves numbers, lists and strings) and a leak check at the end of `differential.tcl` (`dt_leak`, 1.5 million iterations, resident size may not grow by more than 4 MB: one leaked object a time is 70 MB).  28,215 calls, 0 mismatches in the four modes.
* **Measured** (`wallDist` over 146 records of 190 numbers, 12 sectors, ns a record, best of 3, same machine and hour, compiled): 14.9 before, **13.7** now (-8%).  The first part alone (no box at the pop) changed it by 2% only: most of the allocations are the second kind.

## 71. `lappend` and `append` on a variable of the frame (`global`, `variable`, `upvar`) are typed

## 72. A list of numbers that a callee returns and the caller takes apart is not made: tuples are held unboxed

The roadmap item "the list result of a callee followed by `lassign`" (PHASE-A3, gap 3).  Idiomatic Tcl returns several numbers as a list (`return [list $x $y $z]`) and takes them apart with `lassign` or `lindex`; each call built a list and an object for every component and the caller read them back.
* **Measured before building.**  [measured] A small callee `proc pair {x} {list $x [expr {$x * 2.5}] [expr {$x + 1}]}` called in a loop with `lassign [pair $i] a b c`: **50.4 ns** an iteration, against 1.9 when the three numbers are made in the caller (the cost of a list and two double objects plus the three reads).  The engine's `wallDist` (146 records a call) is the other end: the list result and `lassign` cost 33 ns of 1,713 (1.9%).
* **Change.**  A new kind `Y:<kinds>` (`ykinds`, `yvar`, `ydefs` in the translator): a fixed-shape list of 2 to 12 numbers, one letter a component, `I` (integer), `D` (double) or `W` (either, tagged).  (1) Between a `list` of numbers and the `done` that follows it (nothing else reaches that `done`, the proc does not yield) the slot holds the components in a C structure `ty<slot>_<kinds>` of type `tbc_Y_<kinds>`.  (2) The variant's return kind is `Y:<kinds>` when every return of the proc gives a tuple of the same length (`jy` joins component by component: `I` with `D` is `W`), including a literal list of canonical numbers (`return {0.0 0.0}`, the text of which is what boxing the numbers again gives: `litTuple`); the C function returns the structure by value.  Any other return (text, an object component) makes the return kind an object, and the tuple is boxed at that `done` (`tbc_ylist_<kinds>`, in the generated header).  (3) A direct call of a callee that returns a tuple leaves the structure in the slot when everything that reads the slot understands it (`dup`, `listIndexImm` with a constant index inside the tuple, the rest thrown away by `lassign` (decision 56 and 68), a `return`; `slotUsers` decides), else the list is made at the call.  (4) The entry from the interpreter, the resume entries and the re-entry from the boxed code box the structure.  (5) Hand-over boxes it like any slot (`boxe`); a join with another kind boxes it (`jd`).  The callee's boxed fall-back (a callee that had to leave typed mode) returns its result as an object as before and the caller goes on in boxed code from the instruction after the call.
* **Not done.**  A component that is an object (a variable that may hold text or a non-canonical literal such as `1e30` is held as an object: the engine's `wallDist` returns its distance in one), so `wallDist` itself stays a list; a tuple read by an instruction that does not understand it is boxed by a hand-over to the boxed code, not in place.
* **Tests.**  `yt_*` (30 procs, 1,150 calls in `differential.tcl`: pairs, triples, five-component tuples of integers and doubles, a literal and a computed return in one proc, a callee that also returns text, a callee that takes an object, recursion, `lassign` with too few and too many variables, `lindex` with an index out of range, `end`, negative, `llength`, `string length`, `foreach` over the result, a result stored and appended to, in `if` branches, overflow in the callee, `Inf`, text, hex, both integer limits): 29,908 calls, 0 mismatches in the four modes; `tests/typed.sh` checks that the typed code makes no list for them.
* **Measured** (the small callee above, ns an iteration, best of 7): 50.4 before, **2.8** now (1.8 when written without a call).  Engine, cove frame, the `ceilT` cluster only (15 procs), 96x56, machine busy with a build, compiled with decisions 68 to 71 / now: see PHASE-A4.

## 76. `binary scan` of `f` and `f*` is typed and keeps a proc pure: the float32 helpers are direct calls (the lite rule was not the cause)

The engine's two hot Tcl workloads (the texture decoder `::tq::texc` and the fire twin `::tq::fsim`, TclQuest K74 and K76) were measured by their owner as no faster compiled than interpreted (fire: 247 against 236 ms a step) or 2.4x to 2.9x (texture load), with the Tcl call machinery at about a third of the samples, and the cause was read as the "lite" rule of decision 51: small loop-free helpers (`f32`, `rint`, `fx8`, `fxMul`, `clamp255`, `clampf`) left to the interpreter, so that each call from compiled code would be a full Tcl proc call.  The task was to compile them or use their typed bodies at the call site.  **That is already what happens, and the rule is not what held the engine back.**
* **Lite procs are called directly by compiled callers** [read in source: `tbc_attach_entry` in `include/tbc_hook.h`, the `rc == 3` branch sets `*e->valid = 1` and adds the rename/delete trace, as for an attached proc; `liteProc` only decides whether the interpreter's bytecode is patched with the entry stub; decision 51 says so].  Four measurements on the texture decoder (rock_ceiling, 512x512 levels 8; Tcl 8.6.14, macOS arm64, load 4 to 10 [measured]): (1) a module built with `-DTBC_COV`: in one load `fxMul` has 8,386,560 typed entries, `rint` 1,398,064, `fx8` 262,147, `lbucket` 79,424: direct calls of lite procs, 0 hand-overs; (2) the generated C of `packNormal` calls `rint` as `V_rint_B(...)` behind `tbc_valid_rint` and calls `f32` through `Tcl_EvalObjv` at 9 sites; (3) the same module translated with `TBC_NOLITE=1` (every helper gets the entry): 4,001 ms against 4,254 ms, 6%, which is what the entry stub's own cost explains; (4) `f32` replaced by `return $x` in a copy of the engine file (output crc unchanged on the fixed-point path): 2,372 ms, so the one proc `f32` was 1.9 s of the 4.25 s.
* **The cause.**  `f32` is `binary scan [binary format f $x] f r; return $r` (`f32l`: `f*`).  The typed inline `binary scan` of decision 35 takes the integer formats `c s S i I` only; `f` went through decision 64's call of Tcl's command with the variable written to and read from the frame, which needs a frame (`if (!inframe) goto D`), and the purity analysis counts any `binary scan` with a variable as impure.  So `f32` was not `pure`: its callers could not call it directly and made a Tcl call of it (`csafe` path: `Tcl_EvalObjv`) at every use (1.9 s of the 4.25 s load [measured, item 4]; the calls were not counted: `packNormal` alone, entered 262,144 times, has 9 `f32` calls by its source [read in source], `normalsRef` more per texel), and per row and blur tap in the fire's `blurwrap`/`gradients`.
* **Change.**  (1) `binary scan data f var` and `binary scan data f* var` (literal format, a local variable, data that is an object or a literal) are typed (`binScan`): `f` reads the first 4 bytes as a native float widened to a double (`tbc_bscan_f`, `ScanNumber`'s `f`), stored as a double in a variable of kind `D` or `W`, else into the variable's object (`tbc_st_dbl`, written over when only the variable refers to it); fewer than 4 bytes hands over before anything changed, and the boxed code does what Tcl does (nothing set, 0 returned); a variable that holds integers only (`f32` of the fire has its argument as the variable) is widened by the analysis (a `D` store, one round of hand-over), `f*` builds the list of doubles (`tbc_bscan_fl`, none: the empty object).  (2) A proc whose only `binary scan` is one of these is pure (`scanF` in the purity analysis): the command is still in the guard's table (`tbcOwnFrameBuiltins`, so renaming, replacing or tracing `binary scan` or `binary` invalidates it, decision 19), and a call without a frame that has to hand over reports it to the caller as every direct call does (decisions 19, 73).  Nothing else changed: `liteProc`, `liteWeight`, the entry rule and the integer scan formats are as they were; calls from the interpreter behave as before.
* **Measured** (texture load, compiled module before/after, ms; load 4 to 10, three loads of rock_ceiling and one of each other texture [measured]): rock_ceiling 3,962 / 4,199 / 4,419 to 2,846 / 2,982 / 3,173 (1.39x); dressed_limestone 512 4,714 to 3,252 (1.45x); hewn_rockwall 1024 17,418 to 12,116 (1.44x).  Interpreted 11.4 s, 11.9 s, 47.9 s: compiled is now 4.0x, 3.7x, 4.0x; the C twin 13.5 ms, 13.3 ms, 58.2 ms.  The crc32 of all 8 levels of each texture is the same for the interpreter, the module before, the module after and the C twin (24 of 24). The five crc32 (stats, T, both sprites, the drawn frame) are identical for the interpreter, the module before, the module after and the C twin.  The fire is still 1,500 times the C twin: the same next cause as below (allocation of list elements by `lmap`, `lrange`, `concat`, `lappend` and `lindex` per row and blur tap, 28% in the K74 profile; `TclParseNumber` of `lindex` indices 5%) was not re-profiled after this change [not measured].
* **Still not fast: the next cause** [measured: `sample`, 8 s, main thread 6,129 samples, rock_ceiling x6, module after this change].  (a) `TEBCresume` 14.8% and `Tcl_EvalObjv` 1.9%: 478 + 295 + 78 + 14 of the 910 `TEBCresume` samples are under `G_fxRgb`, `G_fxPageE`, `G_fxPages`: the boxed generic code of three procs that hand over once per call at an `unsupported` instruction (`TBC_COV`: `fxRgb` `invokeStk1 fxPlanes` and `lappendList`, `fxPageE` `invokeStk1 fxUp`, `fxPages` `lappendList`) and then run the per-texel loop in the boxed code, calling `fx8`, `fxMul`, `fxWcol` through the interpreter at every texel (the interpreted lite bodies, as they should be there). ## 77. `lappend` of several values is typed; typed code enters again at a loop head with table arrays and integer vectors; a callee that uses `upvar 1` no longer makes its caller unsafe (texture decoder 2.1x)

Decision 76 left the texture decoder (`::tq::texc`, module TEXC, fixed-point path) with 14.8% of the time in the interpreter running the boxed code of `fxRgb`, `fxPageE` and `fxPages`.  The task was to find exactly why each hands over and keep the per-texel loops typed.  Three causes, each measured alone [read in source: `TBC_REPORT` of the module and `tbc::hot` of a `-DTBC_COV` build; `sample` for the split of the time].

* **Cause 1: `lappend l a b c` had no typed code.**  The bytecode is `list 3` then `lappendList` (a list of the new elements appended to a local); only `lappendScalar` (one element) was typed.  `fxRgb` (`lappend out [fx8 $r] [fx8 $g] [fx8 $b]`) and the inner loop of `fxPages` (`lappend t [lindex ...] ...`) therefore handed over in every iteration, and after the first hand-over decision 47's rule (the boxed code does not enter typed code again at the head it was entered at, to stop the two going back and forth) kept the rest of the call boxed [read in source: `tbc_noosr`; the effect is inferred from `tbc::hot` (resumed once, handed over every iteration) and the timing below, not traced iteration by iteration].  Now `lappendList` on a local (kind B) is typed (`tbc_lappendl`, `include/tbc_runtime.h`: `Tcl_ListObjAppendList` on the variable's list, copied when shared, made when unset); the result slot is the list as for `lappendScalar`; an error goes to the boxed code, which repeats the instruction.  `lappendList` is added to the variable operations that cannot run a script on a local (`tbcVarOps`) and its stack effect is declared (1 in, 1 out).  Measured, TEXC compiled (ms, best-of loads; load 3 to 5, same machine, same module build recipe): rock_ceiling 2,691 / 2,706 / 2,806 to 2,104 / 2,143 / 2,243; dressed_limestone 2,946 to 2,391; hewn_rockwall 11,112 to 8,951 (1.24x).
* **Cause 2: typed code could not enter again at a loop head when the proc held a table array (kind R) or an integer vector (kind A).**  `fxPageE` calls `fxUp cq` (`fxUp` links `cq` with `upvar 1`, so the call has to be made by the interpreter and the proc hands over there), and the loops after it are outermost loop heads where the boxed code may enter typed code again (decision 23); but `resumePoints` allowed only the kinds I D B F W for the variables assigned on some path to the head, and `fxPageE` has `cq` and `lev` (R) and `dl` (A).  So `fxPageE` ran its 4096-element loops boxed on every one of the 64 pages (`tbc::hot`: typed entries 64, resumed at a loop head 0; 32% of the samples were self time of `G_fxPageE`) [measured].  Now (a) a table array that is assigned on some path to the head but **not used by any instruction reachable from the head** is skipped (typed code never looks at it; the frame keeps what it has); (b) a table array **assigned on no path to the head** but used after it is allowed when the frame variable is unset at run time (else typed code does not enter: `giveup`, the boxed code goes on, which is what happens for any variable of a kind it cannot take); (c) an integer vector (`A`) is read from the frame: the variable must hold a list of integers in canonical form (`tbc_ivec_check`, then `tbc_ivec_import` once every check has passed), as typed code would have made it.  A table array that is used after the head and was assigned before it is still refused (taking an existing frame array into a table would not give back the order of its elements, which `array names` shows).  Measured on top of cause 1: rock_ceiling 1,488 / 1,527 / 1,607 ms; dressed_limestone 1,771; hewn_rockwall 6,877 (1.30x of cause 1's result).
* **Cause 3: a proc that calls a proc with `upvar 1` was not caller-safe, so its typed callers handed over at the call.**  "Caller-safe" (decision on `csafe`: a typed caller may call the proc through the interpreter and keep its variables in C locals) required every callee to be caller-safe as well; but a callee that only links to variables of *its caller* by `upvar` of level 1 (the default) cannot reach the variables of the caller's caller.  So `fxPlanes` (calls `fxLift`, which does `upvar 1`), `fxPageE` (calls `fxUp`) and through them `fxRgb`, `fxRed`, `fxPages` were not caller-safe and `fxRgb`, `fxPages` handed over at their calls of them.  Now there is a second analysis (`csafe1`: caller-safe but for `upvar` with the literal level 1, and everything it calls is in the same set) and a proc is caller-safe when its own code is and all its callees are in that set.  A callee with `upvar 2`, `uplevel`, a level in a variable, or any unknown command stays unsafe (tests below).  The call of `fxUp` itself from `fxPageE` still hands over (it reaches `fxPageE`'s frame by name); cause 2 makes that cheap.  Measured on top of causes 1 and 2: rock_ceiling 1,279 / 1,278 / 1,323 ms; dressed_limestone 1,386; hewn_rockwall 5,339.
* **Result** [measured: `harness-texc.tcl`, module TEXC, load 3 to 5]: rock_ceiling 2.69 s to **1.28 s** (2.1x; interpreter 11.4 s before decision 76's change and unchanged, so 8.9x; C twin 15.7 ms in this run), dressed_limestone 2.95 to 1.39 s, hewn_rockwall 1024 11.1 to **5.34 s** (2.1x; interpreter 47.9 s, 9x; C twin 66.6 ms).  The crc32 of all 8 levels of the three textures equal the C twin's (24 of 24) and the interpreter's (24 of 24; interpreter run at load 5: 15.0 s, 15.2 s, 56.1 s).  (The "before" column is decision 76's translator rebuilt here: 2.69 / 2.95 / 11.11 s; decision 76 reported 2.85 / 4.71 / 12.1 s on a busier machine.)
* **A limit found, not fixed** (it is older than this decision) [measured with the tree before it, `/tmp/d77/old`]: the typed caller of a caller-safe callee that is **redefined at run time** (after the module was built) to reach the caller's frame does not see the change: `proc e_leaf {} {array set a {k 1}; return $a(k)}` and `proc e_outer {n} {set x 100; ... incr s [e_leaf] ...; return [list $x $s]}`, then `proc e_leaf {} {uplevel 1 {set x 77}; return 1}`: the interpreter gives `77 3`, the compiled module `100 3` (the caller keeps `x` in a C local; the call through `Tcl_EvalObjv` has no validity check, and the stub that makes an ordinary call after a failed `tbc_valid` check goes on in typed code too). ## 78. A typed caller hands over at a call when the callee, or anything it calls, is no longer the definition the translator analysed (found by decision 77)

Decision 77 found a gap older than itself: a typed caller keeps its variables in C locals across a call of a callee that the translator showed cannot reach them (a *caller-safe* callee called through the interpreter, a *pure* callee called directly).  If the callee is redefined at run time so that it does reach them (`uplevel 1`, `upvar 2`, `info level`, `uplevel` into a variable), the caller kept a stale value: interpreter `77 3`, compiled `100 3`.  Two differential lines that show it had been taken out of the tests; they are back, with about 90 more (`tests/differential.tcl`, from the line "decision 78").

* **Where the typed code looked at nothing [read in source, `stepInvoke`].**  (1) The call of a caller-safe callee through `Tcl_EvalObjv` had **no check at all**.  (2) A direct call of a pure callee is guarded by the callee's flag `tbc_valid_*`; when the flag was 0 the stub (`C$pc`) made the call the ordinary way **and went on in typed code** (tbc_st 3 means "the callee wants an ordinary call", whatever the reason).  (3) The flag is also 0 for a callee that is merely armed for its first call (the interpreter attaches compiled bodies lazily), so "flag 0" could not be taken as "redefined".
* **What it is now.**  The flag has three values (`include/tbc_hook.h`): 1 the definition is the compiled one and attached (a direct call needs this, as before); **2 the definition is the compiled one (same text, namespace and arguments) but armed for its first call** (set by `tbc_arm_hook`, with the same `rename delete` trace the attach adds, so renaming it away clears the flag); 0 it is not (redefined, renamed, deleted, demoted, not defined yet).  Every typed call site of a caller-safe or pure callee first asks `tbc_cl_ok` over a static array of the flags of **the callee and of everything it calls, directly or not** (`closureOf` in `translate.tcl`; a callee two levels down can be the one that is redefined) and of the namespace-import alias of the call (`tbc_alias_ok`, which the csafe path did not check either).  If one is 0, the caller **hands over at the call** (`goto D$pc`: locals and stack into the frame, the boxed code makes the call with the variables where `uplevel` finds them), and typed code goes on at the next loop head as for any hand-over.  For the direct call the check is in the stub, after the "no frame" return, so a callee two levels down that reports tbc_st 3 is judged by the caller that has a frame; the fast path (`tbc_valid_* != 1`) is unchanged in cost.  `tbc_ysafe_now` now tests `!= 1`, as before.
* **A second thing found on the way [measured].**  `tbc_by_body` holds one entry per (namespace, arguments, body), so two procs of a module with the *same body* (here `rd_leaf` and `rd_gleaf`) were both attached to the first one's entry and the second's flag was never set: direct calls of it were ordinary calls for ever (an old, silent loss; with the check above it would have become a hand-over per call).  Entries with one body are now chained (`sameBody`, last field of `TbcEntry`) and a definition is attached to the entry of its own name when there is one.
* **Tests.**  `tests/procs.tcl` (`rd_*`: a caller-safe leaf, one two levels down, a pure leaf called directly and through a pure middle proc, a callee that redefines the leaf from inside a loop, two locals) and `tests/differential.tcl`: the two removed lines; 16 redefinition bodies (`uplevel 1`, `upvar 1`, `upvar 2`, `uplevel 2`, `uplevel #1`, `#2`, `incr`, `unset`, `info level`, `info level -1`, `info vars`, a plain return, an error) for each of the leaf, the grandchild and the pure leaf; the same text defined again (compiled code back); renamed away and back, deleted and defined again, a swap inside a loop, execution traces on the callee (`enter`, `leave`, a trace callback that does `uplevel 2`). ## 79. `binary format f` and `f*` are typed: the engine's float32 rounding idiom is a double rounded in C, and the scan reads it back without bytes

The engine rounds to float32 with `binary scan [binary format f $x] f r` (`f32`, `f32l` of `firesim.tcl`, `texc.tcl`).  Decision 76 typed the scan, but the format was still a call of Tcl's command that made a byte array per use (about 17% of the texture decoder's self time in decision 77's profile, and the fire's `f32` calls).  With no Tcl change (batch 352), the translator now recognises the two commands:
* **`binary format f X`** with `X` a double (kind D) or an object (kind B) is typed (`binFormat`).  The result is a *pending* float32, kind `P`: the double rounded to float32 in C (`tbc_f32_round`), in the slot's `sd`.  `binary scan DATA f VAR` with such data stores that double into `VAR` and does nothing else (binScan): there are no bytes and nothing can fail.  Any other use of the value gets its four bytes (`boxe` of `P` is `tbc_f32_bytes`), so the kind never escapes into a frame, a call or a return as a number.
* **`binary format f* L`** with `L` an object is typed too, but makes its bytes in C (`tbc_f32_bytes_list`, a byte array of kind B): the list form is not pending, so a list of rounded values is still scanned as the existing `tbc_bscan_fl` does.
* **Semantics** [read in source: `FormatNumber` and `ScanNumber` in tclBinary.c of 8.6.14].  A double with |d| above FLT_MAX becomes FLT_MAX with its sign, and an infinity too: **Tcl does not overflow to Inf, it clamps** (the task brief said Inf; the source says FLT_MAX).  Otherwise the value is `(float)d`, so NaN keeps its sign and payload as the cast gives.  An object is read by `Tcl_GetDoubleFromObj`, and a double object that Tcl refuses (NaN) takes its internal double, as FormatNumber does.  Anything else (a string that is no number, a bad list) makes the step hand over before anything is changed, so the boxed code raises Tcl's own error.  The guards of a built-in call apply (an execution trace on the ensemble, `depCheck`).
* **Not typed:** an integer, wide or literal argument (the generic call does it), any other format (`f2`, `r`, `binary format f` with a count), and the scan of a pending value in a format other than `f` (the value is boxed first).
* **Tests.**  `f9_*` in `tests/procs.tcl`, with about 240 differential calls in `tests/differential.tcl` (the float range's edges and 2^24+1, 1e-45 and 7e-46, -0.0, NaN, Inf, strings, a list of mixed values, a pending value boxed, a pending value kept in a variable, a scan with the wrong format, a loop, a trace on `binary` and on `::tcl::binary::format`, the format replaced by a proc).  The whole differential is 31,263 calls and 0 mismatches in four modes.  `tests/f32idiom.sh` (in `run.sh`'s list) builds a `-DTBC_COV` module and checks: the double variant of the helper rounds in C and makes and reads no bytes; 1000 calls of each helper from a compiled loop enter the typed code each time with no hand-over; a non-number raises the interpreter's error; the values before and after the loop are the same.
* **Found on the way, not fixed (predates this decision).**  A replaced `binary` **ensemble** (`rename binary binary_x; proc binary ...`) is seen by a call of the helper from a compiled loop in neither the original nor this translator (the counting proc is called 0 times; the same code's own `binary format` in a proc called from the interpreter is seen, 15 of 15 calls).  The guard that catches the replacement (`depCheck`, the ensemble pin) is checked only when the caller's revision changes, and a loop of direct calls does not change it.  [measured with `g.tcl`-style driver, original and new translator alike.]  A test of it is left out of `f32idiom.sh`; the cure belongs with the ensemble guard and is for a later decision.
* **Measured:** not yet.  The texture and fire harnesses (`docs/research/tcl-aot-engine/texc`, `fire`) were not run in this decision; see the handoff note.  The number of object allocations removed per `f32` call is one byte array (the `binary format` result), and the call itself is no longer a Tcl command.

## 80. Flat storage for lists of numbers, first part: objects appended to a native integer vector, and `lset` that writes the element over (texture decoder 1.25x)

The task (K77, D1 decided as option (b): transparent flat numeric storage behind ordinary lists, no Tcl change) was the flat storage of PHASE-A4 section 5 for the two engine workloads.  **This decision lands a first, sound part and says what is left.**  What was found, and why the whole design was not built here, comes first.

* **What the existing machinery already does** [read in source].  A local variable that is only built by `lappend`, read by `lindex`/`llength`/`foreach`, changed by `lset` and returned is held as a native vector of integers (kind A, decision 36), and typed code enters again at a loop head with one read from the frame (decision 77).  The kind is chosen once per variant: a `lappend` of anything but an integer makes the variable an ordinary object list for the whole variant (the `dead` result at the step widens the kind).
* **Measured before changing anything** [`sample`, hewn_rockwall, module TEXC from decision 79, main thread, self samples by owner]: `fxLift` 25%, `fxUp` 14%, `fxPageE` 10%, `buildRef` 8% (boxed), `codeBand` 7.5%; the allocator and object release (`TclThreadAllocObj`, `CreateHashEntry` is `TclFreeObj`'s path, `pthread_getspecific`) about 20% of the total.  The texture decoder after decision 79 is 4.0 s for hewn_rockwall (decision 77 said 5.3 s; decision 79 removed the `f32` bytes), 0.92 s for rock_ceiling.  `fxLift` kept `e` and `o` (`lappend e [lindex $P ...]`, then six `lset` passes over them) as Tcl object lists, because the value appended is an object read from the frame variable `P` (kind B, not I), and every `lset` of a number into `P` made an integer object.
* **Why not the cache of PHASE-A4 section 5, nor a new object type** [argued, not built].  A shadow keyed by the list object and held alive by a reference of the cache makes every `lset` and `lappend` of the program copy the whole list (the object is shared as long as the cache holds it): `lset P $i ...` in a loop over 1M elements would be 1M copies of 8 MB.  Only a read-only shadow is cheap, and a read of an element of an object list already makes no object (the list holds them): the experiment recorded in decision 65 (read a list element as a number in place) gave 13.8 against 13.7 ns a record.  What costs is making elements: `lappend`, `lset` and `lmap` of numbers.  Those need the numbers to live without objects, which a shadow cannot give; a new `Tcl_ObjType` that holds a flat array would (the interpreter's own commands convert it back to a list through its string form: `llength $P` on it is a parse of the whole list), and its cost on code that mixes compiled and interpreted access is not known; it was not built.
* **Change 1: an object appended to a native vector** (`lappendScalar` on kind A with an operand of kind B or W).  An integer in its canonical text (`tbc_arg_int`, the check that decision 77 uses for the entry at a loop head) goes in as the number (`tbc_ivec_push`); anything else (a double, text, `007`, `0x10`, `1e3`, a list, no memory) hands over at the instruction before anything changed, and the boxed code appends the object to the list that the hand-over makes of the vector.  **Only in a proc with no sign of floating-point numbers** (`floaty` false and not the tagged-number variant): such a proc already takes an object operand of its arithmetic for an integer and hands over at the first double (decision 41), so the rule adds no new assumption; a proc with doubles keeps its list as an object list, as before.  A first version without that gate made `normalsRef` (doubles through `lindex`) hand over on its first append and run its whole loop boxed: rock_ceiling 0.92 to 1.2 s, hewn 4.0 to 5.2 s [measured].  A proc that adapts (`wadapt`) notes a double (`tbc_wnote`), so its tagged-number version is used from the next call.  `fxLift` of the texture decoder and `dil` of the fire (mask set-up, not the step) now hold their lists as vectors; the fire's step procs are all floaty, so this change does not touch them.
* **Change 2: `lset` of a number at an integer index writes the element over** (`tbc_lset_ii`, `tbc_lset_id`).  The list is unshared and has no string form (as for `tbc_lset_i`), the element is an integer (a double for `tbc_lset_id`) and **its reference count is 1** (only this list holds it, so nothing can see the object; the same argument as `incr` on an unshared integer and decision 69): the value is written into it, no object is made and none is freed.  Any other case makes a new object as before.  The value of an `lset` is no longer boxed first when it is an integer or a double.  `lrepeat n 0` shares one object among all elements, so the first `lset` of each position makes an object; the passes after it make none.
* **Tests.**  `vb_*` in `tests/procs.tcl` and about 430 differential calls (31,685 in all, 0 mismatches in four modes): the lifting step over lists with doubles, text, `007`, `0x10`, `1e3`, `" 5"`, `{}`, bignums, a list as element, empty and short lists, a list held by another variable, with a string form, lifted twice, an element held by a variable or a nested list when it is set, a shared list, integers and doubles at every index form (`end`, `-1`, `abc`, `1.5`, `{0 0}`, out of range).  Mutation check: with the reference-count test removed from `tbc_lset_ii` the differential test fails.  `tests/vecobj.sh` (in `run.sh`'s list): the report shows `e` and `o` of the lifting step as vectors (it fails on the translator before this decision), a compiled loop of lifting steps never hands over inside `vb_lift`, and a double in the list hands over and gives Tcl's result.
* **Measured** [module TEXC and FSIM from the frozen engine copy, same harnesses as decisions 76 to 79, interleaved runs of the tree before (2d84d13) and this one, Apple arm64, load 1.4 to 2].  Texture load, ms: rock_ceiling 943 / 972 / 1,024 to 805 / 827 / 808; hewn_rockwall 4,087 / 4,167 to 3,277 / 3,222 (1.25x; the two parts alone: 3,660 for the `lappend` part, 3,160 with `lset` in place); the interpreter 11.3 s and 46.3 s, the C twin 13.0 ms and 56.5 ms (hewn is now 57 times the C twin; decision 77 reported 80).  The crc32 of all levels of the three textures equal in the interpreter, the module before, the module after and the C twin (24 of 24).  **The fire is unchanged**: 174.4 / 198.5 ms a step before and 173.0 / 198.0 after (best / median of 20 steps, noise 1%), the interpreter 221.7 / 252.8 ms, the C twin 0.104 ms; the five crc32 (stats, T, both sprites, the frame) equal in all four.  Its step procs are all floaty (doubles through `lindex`, `lmap`, `concat`, `lrange`, `lappend {*}`), which neither change reaches; the fire's `lset A $i [f32 ...]` stores an object that `f32` returned, so the in-place write does not apply to it either.
* **What is left of D1** (not built; it needs the design below, a larger job than this decision).  (1) A vector kind for lists of doubles and mixed numbers (16 bytes an element, a tag and a value, used where the proc has the tagged-number policy), with `lindex`, `lset`, `lappend`, `foreach` and the hand-over/entry/free sites of kind A (about 30 places); the engine's float lists (the fire's T and slabs, `mipRef`'s texel list) depend on it.  (2) `lmap`, `lrange`, `concat`, `lappend l {*}$x`, `lrepeat` on vectors: the fire's rows are made with them. ## 81. The fire's gap was not list storage: an unbraced `expr` keeps `fstep` out of typed code; index words `$i+1` of `lindex` are integers (fire 173 to 27 ms a step with one engine brace moved; the vector kind for doubles is not built)

The task (K77, D1) was a native vector kind for doubles, on the reading that it is "the fire's whole gap".  **Measured first, and it is not**: this decision lands what the measurement found, and says what is left of the vector kind.

* **Where the step went** [coverage build of the fire module, `tbc::hot`, and `sample`, 20 Nov 2026].  `fstep` was entered typed once a step and handed over at its first cell: `exprStk` at pc 3376, 2 hand-overs and 2 resumes a step, after which **the whole step ran as boxed code**. The slot is an integer, read by the `listIndex` of a native vector or of a list object (`tbc_lindex_i`, which already handles every out-of-range index as `lindex` does).  Tagged numbers (`W`) are not folded (the translator did not reach it in any tested proc: left to the boxed path).  In the fire module the strings made by `strcat` in `fstep` fall from 48 to 4 sites.
